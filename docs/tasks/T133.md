#### T133 CI runs on pushes to release branches

- **Design milestone**: M20 (packaging and release). The first item on the `release/0.4` maintenance line ([release-plan.md §2.2.2](../release-plan.md#222-two-release-lines-a-maintenance-branch-per-patched-minor), the user's decision of 2026-10-04 after `v0.4.1`): no v0.4.x after `v0.4.1` is cut until a push run on `release/0.4`'s tip is green, and today a push there runs nothing. **Labels**: `phase:3 lane:infra release:v0.4.2`
- **Branch**: `task/T133-ci-release-branches`, created and pushed by the main session from `origin/release/0.4` ([build-process.md Appendix C](../build-process.md#appendix-c-the-run-task-skill), maintenance-line overrides) · **Model/effort**: Sonnet / Low ([§3.3](../build-process.md#33-model-selection): the OpenCode default, then Sonnet) · **Reviewer**: the complex tier ([§3.4](../build-process.md#34-why-the-reviewers-model-differs-from-the-implementers)): GPT-6 Sol at `low`
- **Start after**: `release/0.4` exists (created from `v0.4.1`'s commit) · **Merge after**: none. It is **never in flight with** another task or fix that edits `.github/workflows/ci.yml`.
- **Owns**: `.github/workflows/ci.yml`: **only** the `push` trigger's `branches` list and the comment above it.
- **Scope**:
  - **Protects**: every job in `ci.yml` runs exactly as before, on `main`'s pushes and on every pull request; the only change is that a push to a `release/**` branch now runs the same jobs. Forbidden: any change to a job, a step, the `pull_request` trigger, or any other file.
  - **The change.** `push: branches: ["main"]` becomes `["main", "release/**"]`. The comment above it says why: a push to a maintenance line must be checked, since a v0.4.x is cut from that line's tip. A PR from a same-repo branch into `release/0.4` still runs twice on one SHA only if that branch is itself named `release/**`, which no task or fix branch is.
  - **Both lines.** It merges on `release/0.4` first (`--base release/0.4`, `Refs #696`), then is ported to `main` by a cherry-pick PR that closes the issue, as §2.2.2 describes.
- **Done when**:
  1. `git diff --name-only origin/release/0.4...HEAD` lists only `.github/workflows/ci.yml`, and `git diff origin/release/0.4...HEAD` changes only the `push` trigger's `branches` line and its comment.
  2. The PR's own CI run (the `pull_request` event) is green.
  3. **After the merge to `release/0.4`** (the main session, as part of this task's merge): `gh run list --branch release/0.4 --event push --limit 1 --json conclusion,headSha` shows `success` on the merge commit. The PR comment quotes it.
  4. **After the port merges to `main`**: `gh run list --branch main --event push --limit 1 --json conclusion,headSha` shows `success` on the port's merge commit, and `.github/workflows/ci.yml` is byte-identical on `origin/main` and `origin/release/0.4` (`git diff origin/main origin/release/0.4 -- .github/workflows/ci.yml` prints nothing).
- **Hazards**:
  - **A push to `release/0.4` from outside a PR** is never made by an agent. Only the squash merge and the main session's branch creation push there.
  - Done-when 3 and 4 run after a merge, so a failure there is a `fix` ([build-process.md §4.10](../build-process.md#410-the-fix-lane)) on the line where it failed.
