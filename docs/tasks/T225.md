# T225 — Partial whole-unit admission in Army Transfer

Correction for #1488. Evidence: [Research85's verified-selection controls](https://github.com/diegoami/imperial-conquest-2-research/blob/24e93f330a634542e68343a069f1585db6e5b117/docs/reports/2026-10-26-partial-army-transfer85.md). Stock-original Wine, not native Windows or general AI/Join-armies evidence.

## Contract

- Each Transfer arrow processes selected **working** rows highest slot first. For each whole unit, check receiver unit count, troop total, then truncated fleet capacity. Append fitting units, compact the giver, continue after refusals, and zero only recipients' working moves. Never lose refused units or roll back accepted ones.
- Show unit-count feedback if encountered, otherwise troop-cap feedback; independently show fleet-capacity feedback. A partial batch is accepted with typed per-unit not-moved information, not falsely reported as a total command rejection. A batch with no fitting units can still confirm the ordinary OK supply rebalance.
- Share one pure admission planner between engine and GUI. Preserve original unit identities and chronological arrow operations so forward/back moves, compaction and appended-unit order replay identically at OK. Opening/staging/Cancel never mutate the campaign. OK submits once and retains existing supply rebalance/empty-army accounting/link policies.
- Add an optional `unit-steps=a0:b,b1:a,...` command form: identities refer to original A/B rosters, destinations are working A/B sides, steps are chronological. It cannot be mixed with legacy unit-index options. Legacy `units`/`back-units` remain supported; their deterministic batch interpretation is selected side descending followed by partner descending. This explicit command sequencing resolves an otherwise unordered two-direction request; it does not assert an original simultaneous two-arrow handler.
- All ownership/adjacency/negative resource/unknown or duplicate legacy index failures remain atomic. Invalid original identities reject before any staged action is committed. Save schemas are unchanged: operation history exists only in this dialog/command, not campaign state. Resource staging, other commands, last-unit safeguards and standalone disband remain unchanged.
- Disband remains a single-unit action: ambiguous multi-selection asks the player to select one unit. Same-dialog Disband transaction lifetime is separately tracked in #1522 and is not certified by this task's unit-transfer Cancel controls.

## Owns

New `Armies/ArmyTransferUnitAdmission.cs`; ArmyTransferCommand/handler unit-admission paths; Army-transfer parser and its accepted-result presentation in GameSession.Commands; ArmyTransferModel/ArmyTransferDialog staging/list/feedback paths; focused engine/model/parser tests and a Godot partial-transfer check. No core command outcome, saves, Join armies, Split, AI, disband handler or disband transaction-lifetime changes.
