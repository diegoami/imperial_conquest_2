#### T131 Every release carries Windows assets: the zip and the installer, built by a release workflow

- **Design milestone**: M20 (packaging), as T27's delivery half. T27 made the export; this task turns every tag into something a player downloads and starts without Godot or the .NET SDK, by the user's decision of 2026-10-04: every milestone **and every fix release** (v0.4.1 and on) gets a GitHub Release with a Windows zip and installer attached ([release-plan.md §5](../release-plan.md#5-release-checklist) item 20, [§2.2](../release-plan.md#22-patch-releases)). **Labels**: `phase:3 lane:infra single-instance` (it exports and launches Godot, [build-process.md §7](../build-process.md#7-concurrency-single-instance-and-local-only))
- **Branch**: `task/T131-release-assets` · **Model/effort**: Sonnet / High ([§3.3](../build-process.md#33-model-selection): not architecture, so the OpenCode default, then Sonnet) · **Reviewer**: the complex tier ([§3.4](../build-process.md#34-why-the-reviewers-model-differs-from-the-implementers)): GPT-6 Sol at `low`
- **Start after**: none · **Merge after**: none (T27 and fix 652 are merged). It is **not** in the `v0.5.0` gate. **It runs next**: the user called it the highest priority on 2026-10-04, so it is the next task dispatched on whichever machine is free, ahead of the v0.5.0 tasks; it does not interrupt a task already in flight. It is **never in flight with** a task or fix that edits `scripts/package.ps1` or `godot/export_presets.cfg`.
- **Owns**:
  - `installer/ic2.iss` (new): the Inno Setup 6 script the main session used for v0.4.0 on 2026-10-04 (below), parameterised by `AppVersion`, `SourceDir` and `OutputDir`;
  - `scripts/release-assets.ps1` (new): builds one tag's two assets, as the Scope says;
  - `.github/workflows/release.yml` (new);
  - `docs/packaging.md`: **only** a new section, "Release assets";
  - `docs/release-plan.md`: **only** [§5](../release-plan.md#5-release-checklist) item 20's wording, if the merged script's or workflow's invocation differs from what this plan wrote.
  - **Not** owned, and not needed: `.github/workflows/ci.yml` (the release build is its own workflow and runs on tags, not on every push) and `scripts/package.ps1` (`release-assets.ps1` calls it with its existing `-Godot` and `-Verify` parameters). If the task finds it cannot work without changing either, stop and report: that is a rework of this entry.
- **Scope**:
  - **Protects**: every tag's GitHub Release carries a runnable Windows x64 zip and installer built from that tag, and nothing else in the repository changes behaviour: no file under `src/`, `godot/`, `data/`, `tests/` or `assets/` changes, `scripts/package.ps1` and `godot/export_presets.cfg` are byte-identical, and `ci.yml`'s jobs run as before.
  - **The model is what the main session did by hand for v0.4.0 on 2026-10-04** (`99ba0d3`): it packaged the tag with `main`'s `scripts/package.ps1` and `godot/export_presets.cfg` copied onto it (T27 merged after the tag), zipped `rendered/export/ic2/` into `ImperialConquest2-v0.4.0-windows-x64.zip` (74.7 MB, the `ic2` folder at the zip's top), built `ImperialConquest2-v0.4.0-windows-x64-setup.exe` (52 MB) with Inno Setup 6.7.3, tested it by a silent install into a scratch directory, a headless launch and a silent uninstall that left no file, and attached both to the v0.4.0 Release. This task automates exactly that, for any tag.
  - **`installer/ic2.iss`.** The v0.4.0 script, unchanged in substance: `#ifndef` defaults for `AppVersion` (`0.0.0`), `SourceDir` and `OutputDir`; `AppVersion` may be any string the tag gives (`0.4.1`, `1.0.0-rc.1`), since Inno Setup treats it as text; a **fixed `AppId` `{5B7E2C1A-6F3D-4E8B-9A41-1C2D3E4F5A6B}`**, so a newer Setup upgrades the same install in place (it must never change, or every player's next Setup installs a second copy); `PrivilegesRequired=lowest` and `DefaultDirName={localappdata}\Programs\Imperial Conquest 2`, a per-user install with no administrator rights; `ArchitecturesAllowed` and `ArchitecturesInstallIn64BitMode` `x64compatible`; `OutputBaseFilename=ImperialConquest2-v{#AppVersion}-windows-x64-setup`; `[InstallDelete]` of `{app}\game`, `{app}\data` and `{app}\assets`, so an upgrade carries no stale file (the player's saves live in the user profile, not there); a Start-menu entry and its uninstaller entry, an optional desktop shortcut (`[Tasks]` `desktopicon`), both with `WorkingDir` `{app}\game`; `UninstallDisplayIcon` the game's executable; `CloseApplications=yes`; and a `postinstall skipifsilent` launch. A header comment says the `AppId` is fixed and why.
  - **`scripts/release-assets.ps1 -Tag <tag> [-Godot <path>] [-Iscc <path>] [-SmokeOnly] [-SkipInstallerTest]`.** It builds; it never touches a Release (that is `-Upload`, below). In order:
    1. **Check out the tag** into a scratch worktree, `git worktree add --detach rendered/release/<tag>/src <tag>`, so the build is the tag's tree and never the working tree's. It refuses a tag that does not exist, and removes the worktree when it ends, pass or fail.
    2. **Overlay the packaging files a tag predates.** For each of `godot/export_presets.cfg` and `scripts/package.ps1`: when the tag lacks it, copy the running checkout's copy (on a dispatch, `main`'s) into the worktree and print `release-assets: <path> is not in <tag>; using <commit>'s`. A tag that carries a file keeps its own. v0.4.0 lacks both. Nothing else is overlaid: a tag whose game code the overlaid files cannot export fails, and is reported, not patched.
    3. **Package.** Run the worktree's `scripts/package.ps1 -Godot <path>` (its repository root is its own parent, so it exports the tag's tree into the worktree's `rendered/export/ic2/`). Add `-Verify` when the tag carries `godot/Checks/AssetPackSelectionCheck.tscn` (`-Verify`'s check scene; v0.4.0 has no such scene) and `-SmokeOnly` is not passed.
    4. **The headless smoke, always.** Copy `ic2/` to a scratch directory outside any repository, and launch `game\IC2.MapViewer.exe --headless --quit-after 600` with `PATH` reduced to the Windows system directories and `DOTNET_ROOT`, `DOTNET_ROOT_X86` and `DOTNET_ROOT(x86)` unset (the same scrub as `package.ps1`'s `Invoke-WithScrubbedEnvironment`; the script carries its own copy, since `package.ps1` is not dot-sourceable). Use `Start-Process -Wait -PassThru`, since the GUI-subsystem executable does not block `&`. It passes on exit 0 with no `SCRIPT ERROR` line in the captured output. This is the check that v0.4.0's build passed on 2026-10-04.
    5. **The zip.** `Compress-Archive` of the `ic2` folder to `rendered/release/<tag>/ImperialConquest2-<tag>-windows-x64.zip`, `ic2\` at its top, as v0.4.0's.
    6. **The installer.** Resolve `ISCC.exe`: `-Iscc`, then `PATH`, then `${env:ProgramFiles(x86)}\Inno Setup 6\ISCC.exe`, then `$env:LOCALAPPDATA\Programs\Inno Setup 6\ISCC.exe` (where the main session installed 6.7.3 per-user); fail with that list when none exists. Run `ISCC /DAppVersion=<tag without its leading v> /DSourceDir=<the ic2 folder> /DOutputDir=rendered/release/<tag> /FImperialConquest2-<tag>-windows-x64-setup installer/ic2.iss`, which writes `ImperialConquest2-<tag>-windows-x64-setup.exe` (`/F` overrides the script's `OutputBaseFilename`, so the name follows the tag exactly, a test tag without a `v` included).
    7. **The installer test**, unless `-SkipInstallerTest`: `setup.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CURRENTUSER /DIR=<scratch>`; step 4's smoke on `<scratch>\game\IC2.MapViewer.exe`; `<scratch>\unins000.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART`, waited for until its process ends (Inno's uninstaller re-launches itself from `%TEMP%`, so wait on that process too); then `<scratch>` holds **no file**. It refuses to run, and says why, when the fixed `AppId` is already registered for the current user (`HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall\{5B7E2C1A-6F3D-4E8B-9A41-1C2D3E4F5A6B}_is1`): the test's uninstall would unregister the player's own install.
    8. **Report.** Print both files' paths, sizes and SHA-256 (`Get-FileHash`), one per line, `release-assets: <file> <bytes> sha256 <hex>`.
    The script exits non-zero on any failure and leaves no worktree or untracked file in the repository outside `rendered/`.
  - **`scripts/release-assets.ps1 -Tag <tag> -Upload [-AssetsDir <dir>] [-DryRun]`: attach, never replace.** It builds nothing; it attaches the two files in `<dir>` (default `rendered/release/<tag>/`) to the tag's Release, deciding from `gh release view <tag> --json isDraft,assets`:
    - **no Release**: `gh release create <tag> --draft --prerelease --verify-tag --title <tag> --notes "Draft created by the release workflow; the release note is written per release-plan.md §4."`, then upload;
    - **a Release, draft or published, holding neither file's name**: `gh release upload <tag> <zip> <setup.exe>`, **without `--clobber`**;
    - **a Release that already holds an asset of either name**: **refuse**. Print `release-assets: refused: <tag>'s release already has <name>; assets are never replaced by the script; re-upload by hand if they must change`, upload nothing, and exit 3. This holds for a published Release above all (v0.4.0's hand-attached assets are the case), and for a draft too: a draft's stale asset is removed by hand (`gh release delete-asset`) before a re-run.
    - **`-DryRun`** prints the decision (`would create`, `would upload` or `refused`, with the reason) and changes nothing; it exits 3 on `refused`, 0 otherwise. It needs no built files.
    `--clobber` appears nowhere in the script or the workflow. Replacing a published asset is the user's act, by hand.
  - **`.github/workflows/release.yml`.**
    - **Triggers**: `push` of a tag matching `v*`; `workflow_dispatch` with a required `tag` input, so an older tag can be rebuilt; and `pull_request` limited by `paths` to `.github/workflows/release.yml`, `installer/**` and `scripts/release-assets.ps1`, which builds v0.4.0's assets and uploads them as workflow artifacts only (`actions/upload-artifact`), never to a Release. The `pull_request` lane exists because GitHub dispatches a `workflow_dispatch` workflow only once its file is on the default branch, so the PR cannot test itself by dispatch.
    - **Runner**: `windows-latest`, Windows Server 2025. Its image ships Inno Setup: [the runner image's Windows 2025 README](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md), image `20260927.275.1`, lists **InnoSetup 6.7.1** under Tools (checked 2026-10-04). The workflow still runs `release-assets.ps1`'s `ISCC` lookup, and installs it with `choco install innosetup -y --no-progress` only when the lookup fails, so an image change does not break a release. **Permissions**: the workflow's top level is `permissions: contents: read`, which every job inherits; only the `attach` job (below) is granted `contents: write`. `concurrency` keyed on the tag, so two runs never upload to one Release at once. `timeout-minutes: 45`.
    - **Godot**: the 4.7.2 .NET editor, got as `ci.yml`'s `godot-headless` job gets it, but the Windows build: `https://github.com/godotengine/godot/releases/download/4.7.2-stable/Godot_v4.7.2-stable_mono_win64.zip`, unzipped with its folder kept whole (`GodotSharp\` must sit next to the executable), cached with `actions/cache` keyed on the version. **Plus the export templates** that `docs/packaging.md`'s prerequisites name, `4.7.2.stable.mono`: `Godot_v4.7.2-stable_mono_export_templates.tpz` from the same release (a zip), whose `templates\` folder's contents go to `$env:APPDATA\Godot\export_templates\4.7.2.stable.mono\`, cached the same way. The implementer confirms both asset names on the release page; the PR states them. `actions/setup-dotnet@v4` with `10.0.x`, as `ci.yml`.
    - **Jobs.** Two:
      - **`build`** (`contents: read`, every trigger): `actions/checkout@v4` with `fetch-depth: 0` (the script needs the tag); then `pwsh scripts/release-assets.ps1 -Tag <tag> -Godot <the console executable>`, where `<tag>` is `github.ref_name` on a push, the input on a dispatch, and `v0.4.0` on a `pull_request`; then the two SHA-256 lines to `$GITHUB_STEP_SUMMARY`; then `actions/upload-artifact` of the two files.
      - **`attach`** (`needs: build`; `if: github.event_name == 'push' || github.event_name == 'workflow_dispatch'`; `permissions: contents: write`; any runner with `pwsh` and `gh`): `actions/checkout@v4`, `actions/download-artifact` of `build`'s two files, then `pwsh scripts/release-assets.ps1 -Tag <tag> -Upload -AssetsDir <the download>`. A `refused` fails the job, by design: the build's files stay on the run as artifacts, and the user decides.
      The workflow never publishes, never edits a Release's title or body, never replaces an asset, and never creates or moves a tag ([release-plan.md §3.1](../release-plan.md#31-naming-and-placement--decided), §3.2: publishing stays the main session's or the user's).
    - **`-Verify` on the runner.** `package.ps1 -Verify` includes a windowed screenshot tour. If it cannot render on a hosted runner, the workflow passes `-SmokeOnly`, and the PR shows the failing log line. `-Verify` stays release-plan.md §5 item 11's local check either way.
  - **`docs/packaging.md`, "Release assets"**: what the two files are and how a player runs each (the zip: extract anywhere, start `ic2\game\IC2.MapViewer.exe`; the installer: per-user, no administrator rights, upgrades in place, saves untouched); how to run `release-assets.ps1` locally and what it needs (the T27 prerequisites plus Inno Setup 6); what the workflow does on a tag push and on a dispatch; the overlay of step 2, naming v0.4.0; and that the `AppId` is fixed.
  - **Out of scope**: code signing (Windows SmartScreen will warn on an unsigned `setup.exe`; the Release note says so, per the v0.4.0 note); macOS and Linux assets; a self-updater; changing what the export contains.

- **Hazards**:
  - **The `AppId` is a contract with every player's install.** Copy it from the v0.4.0 script character for character. A changed `AppId` makes the next Setup a second install beside the first; the reviewer diffs it against this entry.
  - **The local installer test touches the real per-user registration.** The fixed `AppId` means a test on the user's own machine, with the game installed, would upgrade and then uninstall the player's install. Step 7's refusal is the guard; never bypass it.
  - **Tags are immutable** ([release-plan.md §3.1](../release-plan.md#31-naming-and-placement--decided)). The task never creates, moves or deletes a `v*` tag, on the remote or locally, and never edits a published Release. The test tag of Done-when 6 is the only tag it pushes, and the main session pushes it.
  - **Write permission is one job's, on a tag push or a dispatch only.** The workflow's top level is `contents: read`; the `attach` job alone has `contents: write`, never runs on `pull_request`, and runs only the repository's own script. No third-party action beyond `actions/checkout`, `actions/setup-dotnet`, `actions/cache`, `actions/upload-artifact` and `actions/download-artifact`; no secret other than `GITHUB_TOKEN`.
  - **A published asset is never replaced by automation.** The `-Upload` refusal is the guard (Done-when 7); never add `--clobber`, and never delete a published asset to get around it.
  - **Godot downloads are large** (the .NET templates are the bulk). Cache them; an uncached run that times out at 45 minutes is a reason to raise the limit in the PR, not to drop the cache.
  - **The original game's files never ship.** `package.ps1`'s `Assert-NoOriginalGameFiles` (release-plan.md item 13) runs inside step 3 on every tag, overlaid or not; the task never disables it.
