- **Scope**: T106 caps the receiving army's supply at `troops div 100 + 1` and refuses past it (`SupplyExceedsCapacity`), and caps a merged purse at 1,000, spilling the excess to the treasury. The original's `OK` refuses nothing and rebalances supply, and its merge caps nothing. Every rule below is **[confirmed: code, [`2026-10-03-army-to-army-ok-supply-rebalancing.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-03-army-to-army-ok-supply-rebalancing.md) (research `a380a8e`), `TArmyToArmy_OK` `:44572–44649`]** unless marked.
  - **Which army is A.** In the original, A is the army selected when the order was given and B is its partner. Here A is the command's `from` army and B its `to` army [designed: this plan; the two-way case is Hazards' [open] item].
  - **After the units, supply and money are moved**, `OK` runs these steps in this order:
    1. `capA = troops(A) div 100` (`SupplyCapacity.ArmyCapacityTons`; an empty army has capacity 0, because `FUN_0044A698` returns 1 for 0 troops). If `supply(A) > capA`, A's excess goes to B and A is left at `capA`.
    2. `capB = troops(B) div 100`. If `supply(B) > capB` (including what step 1 pushed), B's excess goes back to A and B is left at `capB`.
    3. If A has no units: B takes all of A's supply and **all of A's money, with no cap**, and A is deleted (as T106 already does, with its carried-fleet back-reference sweep).
    4. If B has no units: the same the other way. A `from`→`to` transfer never empties B, so this step is not reachable through the command; it is written for parity.
  - **So supply is conserved exactly**, and when both armies end over capacity, B ends at exactly `capB` and A keeps everything else, above its own capacity. When one army is emptied, the survivor holds all the supply and all the money, uncapped. The rebalancing runs on **every** accepted transfer, a money-only or unit-only one included.
  - **Nothing in `OK` refuses.** `SupplyExceedsCapacity` goes: any amount up to what `from` holds is accepted, and the rebalance places it. The dialog's supply room, `max(0, troops(receiver) div 100 − supply(receiver) + 1)` (`FUN_00442310`), bounds only the dialog's spinner; it is T111's limit, not this command's.
  - **Money is never rebalanced**, and the merge adds it with no cap: the merge's `PurseAccounting.Credit` call and its spill to the treasury go. `PurseCapExceeded` **stays**: it is the dialog's money stepper, `min(step, 1000 − money(receiver), money(giver))` (`:44044–44088`), the only bound the original puts on money moved between two surviving armies.
  - **Everything else stands**: the distance-1 gate, ownership, the 20-unit and 100,000-troop caps (the dialog's per-unit Transfer refusals, `:44091–44250`), and the amount checks.
  - **Both presets.** No user decision makes this a preset difference, and `ArmyTransferCommandHandler` reads no ruleset flag today, so `improved` does not diverge deliberately. The rule applies in both.
- **Done when**:
  1. **The report's worked example.** A and B each hold 30,000 troops (capacity 300) and 500 t. A transfer of 10 talents from A to B leaves A at 700 t and B at 300 t (`S = 1,000`, B at `capB`, A holding the rest). The same armies with the roles swapped (`from` = B) leave B at 700 t and A at 300 t. It fails on `main` (no rebalancing) and passes after.
  2. **One over capacity.** A transfer that leaves only A over its capacity pushes exactly the excess to B. One that leaves only B over pushes exactly the excess back to A. A transfer that leaves both within capacity moves nothing extra. In each case the two armies' supply sums to what it was before.
  3. **No supply refusal.** A transfer of more supply than the receiver's `troops div 100 + 1` is accepted, and the rebalance places it. T106's `Transfer_SupplyOnePastTheReceiverCapacity_IsRejected` is replaced by this test.
  4. **The uncapped merge.** A transfer that empties A into B, where the pooled purse is above 1,000 and the pooled supply is above B's capacity, leaves B with all the money and all the supply, and the treasury unchanged. T106's `Transfer_ThatEmptiesOneArmy_SpillsTheExcessPurseToTheTreasury` is replaced by this test.
  5. **The money stepper stays.** `Transfer_MoneyOnePastThePurseCap_IsRejected` and `Transfer_MoneyExactlyAtThePurseCap_IsAccepted` pass unchanged.
  6. **Every other T106 test stands**, and `CommandCoverageTests` passes with the success golden's `army-transfer` line still accepted. Any changed golden line is explained in the PR.
  7. **Provenance.** `ArmyTransferCommand.cs`'s remarks cite the report's steps and drop the `[open]` on caps.
  8. `dotnet build IC2.sln` and `dotnet test IC2.sln` are green, and the diff lists only Owns paths.
- **Hazards**:
  - **Which army is A when a dialog moves units both ways is [open], for the user.** The original runs one `OK` for the whole dialog, with A the selected army. The command moves units one way only, so a two-way dialog (T111) submits two commands, and the second rebalance runs with its own `from` as A. When both armies end over capacity, the surplus then lands on whichever army the **last** command names as `from`. When they do not, the final split can still differ from a single `OK`, because the rebalance depends on how the supply stood before it. The recommended default is this entry's (A = `from`), with T111 submitting the selected army's own direction last. Exact parity would need a command that carries both directions (for example a `back-units=` list), which is a parser change in the verb files; don't add it here.
  - **The live check is still to come.** The report proposes a Wine run (two adjacent Roman armies, a mercenary unit disbanded in each list, OK) predicting B = `capB` and A = `S − capB`, then the same with B selected, then one that empties A. The rule is [confirmed: code]; if a run disagrees, that is a follow-up.
  - **T72 and the purse.** T72's list of purse writers predates T106 and does not name this handler. After this task the transfer's merge calls no `PurseAccounting.Credit`, so T72 has nothing to change here. If T72 has merged first and changed `PurseAccounting`, keep this task's merge uncapped.
  - **The money stepper's missing floor is not reproduced.** In the original a receiver already above 1,000 gets a negative step (one click moves `money − 1,000` back). The command refuses instead. Say so in the PR.
  - **An army aboard a fleet.** The report did not trace whether an aboard army can be A. Don't decide it; T106's back-reference sweep stays. The dialog's own per-unit refusal when the receiver is aboard and `ships < (troops + unit) div 500` (*"This fleet can not carry any more troops."*) answers #620's N7. It is not folded here.
  - **Split army uses the same form and the same `OK`** (`TUnitMap_SplitArmy` opens `TArmyToArmy` on an empty partner). So a split also rebalances, with the parent as A. `SplitArmyCommandHandler` is T15's and is not this task's; if its result differs, that is a separate bug.
