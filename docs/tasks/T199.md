#### T199 A scenario's own victory condition is checked every round, and a scenario is validated against its world and ruleset

- **Release / priority**: 0.7 series ([release-plan §2.4](../release-plan.md#24-planned-07-series-an-additional-playable-campaign) item 2); P1. Issues [121](https://github.com/diegoami/imperial_conquest_2/issues/121) (substantive), [106](https://github.com/diegoami/imperial_conquest_2/issues/106) item 2, [1028](https://github.com/diegoami/imperial_conquest_2/issues/1028).
- **Start after**: nothing. **Blocks**: T202 (a new campaign states its own goal), T204.

### Problem

`VictoryCheckSystem` evaluates `VictoryEvaluator.Evaluate(state, ruleset, scenario: null)` (`src/IC2.Engine/Victory/VictoryCheckSystem.cs:66`), because `SystemContext` and `TurnCoordinator` carry the ruleset and world but no scenario. A scenario's `victory`, `goal` and `turnLimit` therefore never reach the round tick, the CLI or the AI soak. Load-time validation also sees one document at a time: a custom goal naming an unknown nation or city is accepted and evaluates as `Undecided` for ever (#106), and `recruitment.mercenaryRestockTemplateDrawCount` larger than the world's template table is only refused at the first restock (#1028).

### Scope

1. Carry the resolved `Scenario` through `TurnCoordinator` and `SystemContext` (an optional, nullable member, so every existing construction keeps compiling and old behaviour), and evaluate `VictoryEvaluator.Evaluate(state, ruleset, context.Scenario)`.
2. Pass the scenario at every real execution seam: both `GameSession` constructors (new game and resumed save, which already resolve the scenario by `state.ScenarioId`), the gated tactical coordinator (`GameSession.cs` ~1948), `AiGameRunner`, and the CLI.
3. **Preserve each shipped preset's advertised condition.** `example-classical-improved.json` states `victory: totalConquest` while the Improved ruleset and its New Game card promise domination; today the scenario is ignored, so domination is what plays. Wiring the scenario through without a data change would silently switch Improved to total conquest. **Decided (D1, 2026-10-21):** that scenario's `victory.type` becomes `domination`.
4. Cross-document validation in `GameDataRepository.Resolve` (where world, ruleset and scenario first meet): a `custom` goal must name existing nation and city ids; `mercenaryRestockTemplateDrawCount` must not exceed the world's mercenary template count (when the world has a table). Clear `GameDataValidationException` messages naming the scenario and the field.

5. **A scenario win ends the game in the app** (found during the work: `GameSession` never read `GameWon`; its only ends were the original's falls, holding every city and the hard end year). **Decided (2026-10-21):** a win by a condition other than total conquest ends the game for every seat. Each human seat gets the End of Game window ("You have won the game by …" or "<Nation> has won the game by …"), keeps its control, and the session accepts no further orders. Total conquest and the hard end year keep the original's fall path unchanged.

### Owns

### Done when

1. A scenario with `turnLimit` N ends with `GameExpired` through real round ticks (`GameSession.Submit("end")` repeatedly, not a direct evaluator call), and the same after save → load → continue.
2. A scenario whose `victory` differs from its ruleset's default is decided by the scenario's condition in `GameSession`, in the CLI and in `AiGameRunner` (one test each).
3. The shipped presets keep their advertised conditions: classical-faithful plays total conquest, Improved plays domination (`RulesetPresetsTests` and a new round-tick test).
4. `Resolve` rejects a custom goal with an unknown nation id, an unknown city id, and a template draw count above the world's table, each with a message naming the field; every shipped scenario still resolves.
5. `dotnet build IC2.sln` and `dotnet test IC2.sln` pass; all Godot check scenes pass; CI green.

### Stop conditions

Stop for a plan amendment if threading the scenario needs a save-format change (the scenario is already resolved from `state.ScenarioId` on load, so it should not), or if a shipped preset's played condition would change other than as D1 decides.
