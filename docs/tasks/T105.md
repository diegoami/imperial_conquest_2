- **Scope**: the supply dialog's money panel, `TAFSupply_ChangeMoney`, "moves talents between the national treasury (or a co-located fleet) and the army/fleet, capped at 1,000 money per army or fleet" **[confirmed: `decompiled-unit-map-orders-and-record-fields.md`]**. T38 built the treasury side as a function, `Economy/TreasuryPurseTransfer.cs`, and nothing issues it. This task adds the fleet side and wraps both as one command.
  - **`transfer-money <army|fleet> <amount> [via <fleet>]`**. With no `via`, the other side is the national treasury. With `via <fleet>`, it is that fleet's purse. A positive amount moves money to the named unit's purse, and a negative one moves it out.
  - **The co-located fleet** is an own fleet within Chebyshev distance 1 of the named unit, the supply dialog's provider radius (`TAFSupply_FindProviders`, audit §1.6), or the fleet carrying the named army. It is never the named unit itself.
  - **Limits**:
    - one move is at most **1,000** talents either way; a larger amount is rejected;
    - the purse cap (`EconomyRules.PurseCapPerUnit`) holds on the receiving purse;
    - no move takes more than the source holds;
    - the treasury and purse rules are the ones `TreasuryPurseTransfer` already applies, reused for the fleet side, never copied.
  - Only the active nation's own units, on both sides. A foreign or unknown id is rejected.
  - `TreasuryPurseTransfer.cs`'s remarks say the report never mentions a fleet as the money's other side. The report does name it (above), so the remark is corrected with the code.
- **Done when**:
  1. `TransferMoneyCommandTests`: on the classical scenario, `transfer-money <Rome's army> 100` moves 100 from Rome's treasury to that army's purse, and `-50` moves 50 back. The treasury plus the purse is conserved exactly. It fails on `main` (no command) and passes after.
  2. The same for a fleet.
  3. With an own fleet one tile from the army, `transfer-money <army> 100 via <fleet>` moves 100 from the fleet's purse to the army's, and `-50` moves 50 back. The two purses together are conserved exactly, and the treasury is unchanged.
  4. `via` a fleet two tiles away, a foreign fleet, or the named unit itself is each rejected, with the state unchanged.
  5. An amount of 1,000 is accepted, and 1,001 and -1,001 are rejected. An amount past the purse cap, or more than the source holds, is clamped exactly as `TreasuryPurseTransfer` clamps it, asserted against the function's own result for the same inputs.
  6. A foreign army, an unknown id, and a zero or non-integer amount are each rejected, with the state unchanged.
  7. `CommandCoverageTests` passes, with **accepted** `transfer-money` lines in the success goldens, one with `via`. The CI `OrderCoverageCheck` is green with the mirror entry.
  8. `dotnet build IC2.sln` and `dotnet test IC2.sln` are green, and the diff lists only Owns paths.
- **Hazards**:
  - **The 1,000 is read as a per-move limit.** The report's sentence could also describe the purse cap, which `purseCapPerUnit` already holds at 1,000. This entry keeps both. If a research read settles it as the purse cap only, dropping the per-move limit is a follow-up.
  - **"Co-located" is the report's word**, and the provider radius is this entry's reading of it. If a research read narrows it to the same tile, that is a follow-up.
  - Whether the dialog needs a supply provider nearby before it opens is the UI's gate (T111). Don't add a location gate to the treasury side here.
