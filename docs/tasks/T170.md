- **Scope**:
  - **Protects**: nothing a player sees or the engine computes changes. The terrain **codes** (0 and 1), the move costs (1 and 3), the display name `Sea`, passability, every rule outcome, every golden file, the fixtures corpus, the terrain sidecar, every save and every pixel of every asset are unchanged. Only identifiers change.
  - **The evidence** (the names): [`decompiled-map-code1-overlay.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-map-code1-overlay.md) §4 (research commit `0d2674c`): *"Code 0 is all calm sea, open ocean included, not 'coastal'. Code 1 is transient rough sea, not 'deep'."* The report also says the asset key and the rulesets' rows "carry the same misnomer", and §5's fleet panel reads `Sea-calm` / `Sea-rough`. **The new ids:** `sea_coastal` → **`sea_calm`**, `sea_deep` → **`sea_rough`**; the tile keys become `terrain.sea_calm.tile` and `terrain.sea_rough.tile`, `AssetKeys.TerrainSeaCalmTile` and `TerrainSeaRoughTile`. (Both are renamed: renaming only `sea_deep` would leave `sea_coastal`, which the report calls equally wrong, beside it.)
  - **The surface keys.** `terrain.sea_shallow.surface` names the coast rim of T148's splat map and is **correct** (a thin rim within one cell of land, by distance, not by code); `terrain.sea_deep.surface` is that map's open water, whatever its code, and says nothing of rough sea, but its name would collide with the retired id. It becomes **`terrain.sea_open.surface`** (`TerrainSeaOpenSurface`); `sea_shallow` stays. This is the one name chosen for a reason other than the report's; the user may veto it at the plan PR (then that key keeps `sea_deep` and Done-when 1's search excludes it).
  - **How an old save or world that carries `sea_deep` loads** (checked in `src/IC2.Engine/Persistence` and `Model/GameState.cs`): a save stores `worldId`, `rulesetId`, cell **codes**, the rough-sea cells as coordinates and each fleet's covered code as an integer. It stores **no terrain id**, so no save carries `sea_deep` and **no save-format bump or migration is needed**: a save loads against the world and ruleset shipped in the same build, which hold the new ids. The compatibility rule: *a terrain id is data, not saved state; saves refer to terrain by code.*
  - **Open question 1 (for the user, a real design question):** a **user-authored** world or ruleset (the scenario authoring guide invites them) that still says `sea_deep` would lose its price (`Ruleset.MoveCostFor` falls back to a default, so a fleet's rough-sea cost silently changes) and would fail the world's code lookup. Options: **(a)** no alias, as nothing but our own files carries the old ids before `v0.6.0`: simplest, and the Done-when search finds zero old names; **(b)** one alias at the data loader (where `tileTypes` and `terrain.moveCosts` are read), mapping the two old ids to the new ones with a logged warning, plus one test: the single allowed site in Done-when 1. **Recommendation: (a).** **Decided by the user on 2026-10-13: (a), no alias.** Done-when 1 therefore has no exception.
  - **Out of scope**: the display name `Sea`; the rough-sea overlay itself (T81); the pixels of the tiles (a recolour would be its own task); renaming `sea_shallow`.

- **Why it stays whole** (build-process.md §4.11): an id and its manifest keys, files and tests must change together or the asset and data tests fail; split, `main` would not build or pass between merges.
- **Hazards**:
  - **The exporter is the source of the worlds.** Edit `export-classical-world.cs` and re-run it; a hand edit of the JSON is wrong by the script's own rule. If the DAT is not on this machine, say so in the PR and have the main session run the exporter.
  - **A moved file must keep its bytes:** use `git mv`, and check the manifests' relative paths in both packs.
  - **Do not touch the `Sea` display name or the code numbers**: golden files and the fixtures corpus pin them.
