#### T161 New games start with the original's regiments in training, read from the DAT

- **Design milestone**: M4 (recruitment). Planned from bug [#514](https://github.com/diegoami/imperial_conquest_2/issues/514), which the user reported again on 2026-10-11 while playing v0.5.x ("there are no regiments in training anywhere at the beginning of the game but there are supposed to be some"). It is a task, not a fix ([§4.10](../build-process.md#410-the-fix-lane)), because every new game's starting state changes. **Labels**: `lane:engine release:v0.5.3`
- **Branch**: `task/T161-starting-recruitment`, from `origin/main` · **Implementer and reviewer**: the user's choice ([CLAUDE.md](../../CLAUDE.md) rule 17; the standing pair of 2026-10-11)
- **Start after**: none · **Merge after**: none.
- **Owns**:
  - `scripts/export-classical-world.cs`: **only** reading each DAT nation record's recruitment block and writing it into the world's nations, with its provenance note. A re-run must reproduce every other byte of every output unchanged.
  - `data/worlds/classical-mediterranean.json`: **only** through the exporter, gaining each nation's starting queue.
  - `src/IC2.Engine/Model/World.cs` (`NationDefinition`): an optional `recruitmentSlots` list, defaulting to empty, so every other world loads unchanged. `src/IC2.Engine/Model/GameStateFactory.cs`: **only** seeding `NationState.RecruitmentSlots` from it, where it is `Empty` today (about :90). The world loader and `src/IC2.Engine/Serialization/GameDataValidation.cs`: **only** loading and validating the new field.
  - `docs/scenario-authoring.md`: **only** the row(s) documenting the new world field.
  - `godot/Checks/RecruitTownGateCheck.cs` and `godot/Checks/StrategyDialogsCheck.cs`: **only** their setup or expectations that assumed Rome starts with an empty recruitment queue (about :203, :230 and :579). Either empty the queue in the check's own setup, or count from the starting queue. What each check proves stays the same; each change is listed in the PR with its reason (the implementer's report on PR #1005, 2026-10-12).
  - Tests: the new tests; the CLI goldens (regenerated through the CLI only); **any test under `tests/` whose seeded expectations the starting queues change**, for those values only, each listed in the PR with its reason; `tests/fixtures/cli/success.txt` and T156's `AiTargetTreeDecisionsAreCarriedOutTests.cs` scenario inputs, on the same terms as [T158](T158.md)'s Owns.
- **Scope**:
  - **Protects**: a new game on `classical-mediterranean` starts with every nation's recruitment queue exactly as the original's DAT gives it, slot by slot; any other world, and any save, loads as before.
  - **The rule** ([`2026-09-29-new-game-recruitment-queues-come-from-the-dat.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-09-29-new-game-recruitment-queues-come-from-the-dat.md), **[confirmed]**: three headless new games in Wine, every nation's slots identical to its DAT record):
    - **The DAT.** Each nation record is 1,055 bytes (`0x41F`) from DAT `0x1B100`. Its recruitment block is at `+0x2C9`: 320 bytes, 40 slots of 8 bytes, the words `state, type, troops, city`. An empty slot ends the queue (the report's "non-empty DAT slot"); the implementer states the emptiness test it uses (for example `troops == 0`) and checks it against the report's table.
    - **The mapping.** The state word becomes `RecruitmentSlot.StateCode` (the readiness counter, 0–24). The type code becomes `UnitTypeId` (0 `light_infantry`, 1 `heavy_infantry`, 2 `archers`, 3 `light_cavalry`, 4 `heavy_cavalry`). The troops are copied as they are. The city index becomes the `TargetCityId` of that DAT city, using the same index-to-id mapping the exporter already uses for cities.
    - **No other change.** The slots keep their DAT order. Nothing is appended at export: the extra state-0 slots in the report's games are recruits made by the AI nations seated before the human, which the engine's own AI turns already produce.
  - **Out of scope**: the turn-order shuffle ([T119](T119.md)); what the AI recruits later; `toy-3city` and the other worlds (they keep empty queues).
- **Done when**:
  1. **Rome.** After a New Game on `classical-mediterranean`, before any turn runs, Rome's queue is exactly the report's: light infantry 5,500 (state 9), heavy infantry 3,500 (13), heavy infantry 4,000 (17), heavy cavalry 1,000 (17), all at the DAT's city 85 (by its id), 14,000 troops.
  2. **Every nation.** For all 16 nations, the slot count and the troop total equal the report's table (for example Carthage 2 slots and 4,200 troops; Seleucid 8 and 35,200). The test reads the expected values from a fixture copied from the report, not from the world file under test.
  3. **The exporter.** A re-run of `scripts/export-classical-world.cs` reproduces the committed world byte for byte, and changes nothing but the new fields since `origin/main` (the PR shows the diff summary). The main session re-runs it if the implementer cannot, since it needs the original DAT.
  4. **Other worlds and saves.** A world with no `recruitmentSlots` loads with empty queues, as today. A save round-trips. Validation refuses a slot whose city or unit type does not exist, or whose state is outside 0–24, with the key in the message.
  5. **The app.** The game screen's training view (the Recruit unit dialog, or wherever queued units are listed) shows Rome's four units at game start, through a test or a headless check.
  6. **Nothing regresses.** Every changed golden and seeded expectation is regenerated or updated and listed with its reason. The soak reports 0 rejected. Build and test are green, and the diff lists only Owns paths.
- **Hazards**:
  - **Every seeded `classical-mediterranean` game changes**: units come out of training from the first weeks, armies are larger, and the AI's budget and orders differ.
  - **City index mapping.** A wrong index-to-id mapping would put a queue in the wrong city. Done-when 1 pins Rome's city by its id.
