#### T145 The End of Game window shows the original's text

- **Design milestone**: M18 (the Godot UI), with M12's end of the game.   - **The window's lines, in order** **[derived: code, `THumanFalls_InitializeForm` @ 00455E38, :56383–56473, the report's "What the window writes, label by label"; Wine candidate: confirmed on 17 staged windows W1–W17, per-label OCR, the label strings in game memory and the autosave]**:
    1. `The game is over for <leader> the leader of <nation>.`, in **every** window (not only when no human is left), with the leader the seat had **when it fell**: `SeatFall.LeaderName`, recorded by `RecordSeatFall` before any later write, so a replacement leader (T146) never shows here.     2. The reason: `SeatFall.Text`, the engine's text, unchanged.
    3. So `0 years` and `1 years` never appear. The original's literals are 270 and 269 (`0x10e`, `< 0x10d`, :56418–56419); the clone reads the start year from the ruleset (`calendar.startYearBc`, 270 in the three shipped rulesets) **[derived: the original only ever starts in 270 BC]**. T138's *"<Leader> ruled <nation> for <n> years."* goes.
    4. The table's two column titles: left `<nation> in <startYearBc> BC.` (the original's fixed `in 270 BC.`, :56433), right `<nation> in <SeatFall.YearBc> BC.` (:56454–56458). T138's header row `<nation> | Start | End` goes.
    5. Three rows per column, each one label string: `Population` + the number; `Cities   ` (three spaces) + the count; `Treasury ` + the number + ` talents`.
  - **Population is the wealth field** **[derived: code, :56436–56437 and :56461–56462 read `+0x434` and `+0x430`; Wine candidate: Rome reads 2,577,000 in W1]**: the end figure is `SeatFall.EndWealth`, the nation's `Wealth` at the fall (Rome's 2,577,000, not T138's `Population` of 859); the start figure is `PopulationAtStart × economy.wealthPerPopulationThousand` **[derived: the original's start field equals its current wealth at New Game for 16 of 16 nations (the report's start table), and the shipped world's `wealth` equals `population × 3000` for every one of its 16 nations, so the product is the New Game wealth without a new state field]**. This is the same field mix-up as bug [#742](https://github.com/diegoami/imperial_conquest_2/issues/742) in the nation status panel (`NationStatusModel` prints `Population` where the original prints `+0x430`); the two share the cause (`NationState.Population` is the thousands sum, never updated) but not a file. #742 stays with [T140](T140.md), which owns `NationStatusModel.cs` and reads `NationState.Wealth`; neither task waits for the other.
  - **The number format** **[derived: code, `FUN_00448e74` (:47544) and `FUN_00448f18` (:47581); Wine candidate: the memory strings `Treasury  - 30,000 talents` (W1) and a positive treasury with four spaces after `Treasury`]**: a number is written as three characters, a space, then `-` for a negative value or a space, then a space, followed by the absolute value with a comma before each group of three digits, and no trailing spaces. So 2,200 reads `   2,200`, −30,000 reads ` - 30,000`, and the rows read `Population   2,577,000`, `Treasury    2,200 talents` and `Treasury  - 30,000 talents`. The count of cities is printed bare after `Cities   ` **[derived: the report's label table gives the count with no formatter, :56441–56442, :56466–56467]**. This is the user's decision on #761, not row L14 of #718 (thousands separators on the information panels, `post-v0.5.0`).
  - **Two recorded differences** **[designed: the user's decisions of 2026-10-05 on #761]**:

The original prints its city-count word after the last capture's decrement (4 for the staged Gaul of W13 and W17, 0–5 in a natural conquest), a leftover counter the clone does not keep.
    - **The buttons stay T138's**: Main menu and View map when the game is over, Continue otherwise (approved at T138's visual review). The original's single OK, and the blank main window it leaves when no human is left, are not copied.
  - **Layout** **[designed, a default the user may change at the visual review]**: the first line, the reason and the years line one under another, then the two columns side by side, the start column on the left, each its title and its three row strings, then the buttons. The strings are shown whole; the original's clipping of the reason label under Wine's font is not reproduced.
  - **What `SeatFall` carries.** `RecordSeatFall` fills `LeaderName` from the fallen nation's `LeaderName`, `YearBc` from `State.Calendar.YearBc`, and `EndWealth` from the fallen nation's `Wealth`, from the same nation value each call site already passes (pre-fall for a deposition, post-capture for a conquest). `GameEndViewModel.FromFall` reads the year from the `SeatFall`, no longer from the screen's calendar.

- **Hazards**:
  - **The human visual review** posts screenshots of a windowed run: a deposition at 270 BC (the `short time` line and a negative treasury), the 250 BC window (20 years), a conquered window (Cities 0), the hotseat Continue window and the game-over window with its two buttons. "Looks right" is the user's call (Q-B); it settles the layout.
  - **The leader is a placeholder until T146.** On the shipped classical world every `leaderName` reads `(unassigned -- drawn at New Game)` (bug #762), so the first line names it until T146 merges. That is expected; do not substitute a name.
  - **The start wealth is a product, not a field.** For an imported original save the clone's `PopulationAtStart` is the import's own population sum (`OriginalSaveFieldMapping`'s remarks on the `AtStart` fields), so the product is the import's wealth only as far as that save's wealth is consistent with its cities. Not this task's to change; if the review finds a window figure wrong for a New Game state, stop and report.
  - **The cities count's format** is read from the report's label table, which names no formatter. If the report's memory strings for the cities labels show leading spaces after `Cities   ` beyond the three, follow them and say so in the PR.
  - **A defect in the engine's fall paths** is a bug in merged code: suspend and file it ([build-process.md §4.6](../build-process.md#46-bugs-and-follow-ups)).
  - **Never two Godot processes at once**: run the headless checks one at a time.
