### Product contract

Use the supported engine file logger plus one small local structured breadcrumb journal, no logging framework/service/network/telemetry. Explicitly enable `debug/file_logging/enable_file_logging` (including applicable desktop override), use `user://logs/godot.log`, retain five engine logs, and enable `application/run/flush_stdout_on_print` for release. Validate these keys against pinned Godot 4.7.2; [official logging guidance](https://docs.godotengine.org/en/4.6/tutorials/scripting/logging.html) and [ProjectSettings](https://docs.godotengine.org/en/4.6/classes/class_projectsettings.html#class-projectsettings-property-application-run-flush-stdout-on-print) describe the existing mechanism. It captures emitted Godot output/errors including `GD.PushError`; AppDomain hooks do not intercept all engine errors. Do not promise a native crash handler, stack or last native message that the engine never emits. No active renderer/driver query, shader probe or backend change: retain engine startup-reported backend/adapter/driver if available; otherwise mark unavailable. Driver root cause remains unproven.

Write custom records under `user://logs/diagnostics/` with UTC timestamp, monotonic sequence, run ID, operation correlation and BEFORE/AFTER/failure outcome. [Designed] journal limits: 1 MiB per file, five files total including current, 4 KiB maximum encoded record; rotate safely before append, preserve newest valid records and never scan/delete outside this directory/pattern. Truncate bounded fields before encoding; preserve valid parseable records. Flush every meaningful boundary before executing the operation, not only on normal quit. Guarantee managed buffers are flushed to the OS, with an explicit durability flush at operation boundaries where supported; no power-loss guarantee. Avoid per-render/per-progress polling, background watchdog or timer spam. Discrete tactical frame/stage entries are permitted, including zero-delay/skip; deduplicate unchanged stage/progress notifications. Engine retention is file-count based: its current file has no documented byte-size limit. Document that limitation rather than manipulating an open native engine log; the custom journal's byte cap is mandatory. Do not enable verbose engine spam.

Startup records identify product/build version (development explicitly marked), engine/runtime/platform, pack and available startup backend metadata. Capture screen/overlay changes and focus lost/gained, load/save begin/outcome, allowlisted command kind and safe arguments, turn index, stable nation/entity/battle/frame IDs where safe, half-round/side/controller/general mode, battle/strategic pause-speed settings, frame kind/discrete presentation stage, skip/cancel/finish, terminal/reconciliation/completion and result opening BEFORE/AFTER. Correlate engine/custom logs by run/start time/build without duplicating arbitrary engine output into the journal. Records describing displayed battle state use its immutable frame/snapshot, distinguish authoritative turn context, and never drive state changes. Logging must not reorder submissions, exchange cues, transitions, RNG or completion.

Allowlist record fields and command verbs; never write raw command lines, arbitrary player/unit names, save contents, original assets, credentials, environment variables or full private paths. Save/load targets use a run-local opaque token plus format/category, not basename (which may itself contain a private name). Unknown commands log only `unknown`, never raw operands. Exception records retain type, sanitized bounded message, relevant code-stack frames and inner-cause structure without private path/name leakage; strip source absolute paths and untrusted payloads. Install best-effort managed unhandled/unobserved exception hooks once, unsubscribe on disposal, preserve runtime exception semantics and do not mark unobserved tasks observed solely for logging. Do not globally catch/recover gameplay failures or assume Godot callback exceptions reach these hooks. Controlled tests separately prove managed hook and Godot error persistence paths. Disk-full/access-denied/rotation/write/flush failures disable/degrade diagnostics safely with at most one nonrecursive warning; no throw into gameplay, recursive logging, indefinite retry or UI blocking. No guarantee that storage I/O cannot affect elapsed wall time; avoid fsync in render/progress loops and measure bounded overhead in the test scenario.

README gives `user://` and its current Windows expansion `%APPDATA%/Godot/app_userdata/Imperial Conquest 2 Map Viewer/logs/`, noting actual engine user-data location/overrides, which files to retain after a failure, and that logs stay local. Do not change app name/custom-user-directory settings and thereby move existing saves. Custom logs are sanitized by contract; raw engine logs can include engine-generated paths and must be reviewed before sharing. This is designed diagnostics, not recovered gameplay evidence.
