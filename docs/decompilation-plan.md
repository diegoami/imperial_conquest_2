# Static decompilation plan (Ghidra)

This plans the roadmap's still-open item: *"Analyze the full v1.01 EXE statically, starting from DAT/SAV I/O, end-turn, city changes, movement, combat, diplomacy, AI, and victory messages"* (`roadmap.md` §3). It exists because several mechanics cannot be recovered from save-file diffing at all — combat resolution, AI decisions, and exact cost/income formulas are computed at runtime and never fully serialized. Tooling: Ghidra 12.1.3 + Temurin JDK 21, installed locally under `%LOCALAPPDATA%\ReTools`, kept outside this repository like the game assets. **The executable is not run** — this is static analysis of the same read-only file already hashed in `impconq2-sha256.txt`, consistent with every prior report and the roadmap's explicit constraint that running the original binary is a separate, not-yet-authorized step.

## Why this is tractable

The binary is Delphi (Delphi 2 era), which embeds method-name tables and form resources far more legible than a typical stripped C/C++ build — already proven useful without a decompiler in `battle-code-entry-points.md` (found `TBattleMap.StartBattle`, `MoveHumanUnit`, `EndTurn`, `ComputerGeneral`, `Surrender`, `FinishBattle` and code-to-string cross-references purely from RTTI, before Ghidra was ever installed) and `menu-and-toolbar-inventory.md` (found event handlers `StrategicDecision`, `ChangeNation`, `ShowOnAreaMap`, `UnitMapAction` and the `TMainMenu` stream). Ghidra's headless mode can auto-analyze and export decompiled pseudocode without any GUI interaction, so this is fully drivable end-to-end.

## Setup status: working, with one gap found

Ghidra 12.1.3 + Temurin JDK 21 are installed under `%LOCALAPPDATA%\ReTools` (outside this repo). Headless import and auto-analysis of the full v1.01 EXE succeeds cleanly in about 30 seconds. Decompiling by address works and produces genuine, readable pseudocode — verified by decompiling the seven known `TBattleMap` addresses from `battle-code-entry-points.md`; `StartBattle` (`0x00436fb4`) contains the literal constant `0x1c0` (448), matching the tactical grid's known 14-tile width at 32 px/tile from `battle-observation.md`.

**Gap:** Ghidra's own analyzer does not recover Delphi's RTTI method-name tables automatically — every function comes back auto-named `FUN_xxxxxxxx` unless targeted by an address already known from prior manual byte-level reading (as `battle-code-entry-points.md` and `menu-and-toolbar-inventory.md` did without any decompiler at all). This means:

- [x] **0. Recover Delphi RTTI symbols in Ghidra.** Done: a Python scanner recovered the exact method-table byte format (`Word Count` + entries of `{Word EntrySize; Pointer Addr; Byte NameLen; Name}`, followed by the class name in the same format) by matching it byte-for-byte against the seven known `TBattleMap` addresses, then applied it across the whole 1,166,336-byte EXE. Result: **282 methods across 31 classes**, every one matching a real class name (all 30 `TPF0` forms plus `TObject`), imported into Ghidra as real symbols (`ClassName_MethodName`). This is what made the priority queue below tractable immediately instead of needing a hand-found address per target. See [decompiled-fleet-tax-and-mercenary-formulas.md](reports/decompiled-fleet-tax-and-mercenary-formulas.md).

**A second gap found:** Ghidra's `ReferenceManager`/`getReferencesTo()` does not find code references to several known-real string literals in this binary (tested on the DAT filename and `"falls to"` — both zero results, and a raw byte scan for the address as an immediate operand also found nothing). The earlier successful `SHOOTS AT`/`ATTACKS` lookups worked only because those *addresses* were already known from prior manual work; `getFunctionContaining()` doesn't need Ghidra's reference index, only `getReferencesTo()` does, and that's what's failing here. **Workaround that works:** decompile every function in the application's address range to one text file (`ExportAllInRange.java`, ~1,900 functions took a few minutes) and grep the *decompiled output* for the string — Ghidra's decompiler inlines string-literal operands into the pseudocode even when no formal Reference was ever recorded. This is how the city-capture code was found (see priority item 5). Prefer this whole-range-dump-and-grep approach over `FindXrefs.java` for any string not already tied to a known address.

## Priority queue

Ordered by (value of the unknown) × (how directly a known form/string points at it), each with the empirical numbers already available to cross-check a recovered formula against.

1. [x] **`TBuildFleet` — fleet order cost/capacity.** **Done:** `cost = shipCount × 10` and `capacity = shipCount × 500`, both exact matches to the 10-ship/100-talent/5,000-capacity order. Found one unexplained `shipCount × 3` value. See [decompiled-fleet-tax-and-mercenary-formulas.md](reports/decompiled-fleet-tax-and-mercenary-formulas.md).
2. [x] **`TRecruitMercs`/`TArmyRecruits` — recruitment and mercenary-hire cost formulas.** **Done for standing recruitment, exact match, and the price table itself is now located and fully decoded** in [unit-type-stat-table-in-dat.md](reports/unit-type-stat-table-in-dat.md): `cost = (troops / 200) × priceTable[unitType]`, and the DAT file's own unit-type table (found by searching for the unit-type name strings) gives the literal price values, which match values already algebraically solved-for from two independent save-diffs (1,400 light cavalry: 105 initial/21 quarterly; a 15,000-troop transfer's +75 quarterly delta) — see also [decompiled-recruitment-cost-formula.md](reports/decompiled-recruitment-cost-formula.md). That same table also gives moves, standard battalion size, shots, and range per unit type — all cross-checked against real observations. For mercenaries: confirmed the offer's troops field is set to the `0xFFFF` sentinel in code on hire, confirmed the 100,000-troop army cap as a hard `≥100,001` check, and found `Label` is a name-table index (not a nation code). The mercenary cost formula's exact table values (does it use this same table?) and literal label→name strings remain open. Mobilization (`TArmyRecruits_MobilizeUnits`) delegates to an unnamed helper, not yet decompiled.
3. [x] **`TPolitics` — tax income formula.** **Done, exact match:** `income = nationTaxBase × taxPercent / 100`; solving Rome's own 15%/20% data points both give `nationTaxBase = 2,440` exactly. `nationTaxBase` itself not yet identified as a named field. **Diplomatic reparation formula: dead end via `TPolitics_MakePeace`** — that function only handles the player's own peace proposal (diplomatic-state check, no treasury math); the AI-to-AI reparation seen in saves must be computed in unnamed AI code (`ComputerGeneral` or similar), not reachable by class name the way the rest of this queue was.
4. [x] **`TBattleMap`/`ComputerGeneral`/`FinishBattle` — combat loss formula. Structure confirmed, constants partly open:** traced `ComputerGeneral` down through the AI dispatch chain (found `FUN_004381a4` is unit *placement*, not combat, independently reconfirming the 20-units/army cap) and reached the real shooting/melee resolution functions directly via the known `SHOOTS AT`/`ATTACKS` string references. Melee applies losses to **both sides simultaneously** (matches the structure of the one recorded melee exchange), each side's loss a random-roll term scaled by a unit-type effectiveness ratio and capped at 30,000 and at 40% of that side's own troops; also found a `+2`/`−3` per-side adjustment on an unidentified field (candidate morale). See [decompiled-combat-formula-structure.md](reports/decompiled-combat-formula-structure.md). **Update: `FUN_0043845c`/`FUN_00438420` are now decompiled** (shooting-range and focus-fire-counter helpers respectively, both revealed in the unit-type stat table work — see [unit-type-stat-table-in-dat.md](reports/unit-type-stat-table-in-dat.md), which also supplies the per-type range/shots/moves constants those helpers need). `FUN_0043845c` (shooting) reads `Range` from the unit-type table and a real grid-distance function (`FUN_00449018`) to decide whether a shot is "in range" and gets its effect doubled. `FUN_00438420` (melee) turned out to be a **focus-fire counter** — it counts how many units are currently targeting a given defender, which is what scales both sides' loss multipliers in the melee formula (more attackers on one target = more losses for that target, proportionally less for each individual attacker). **Update: the two-dimensional `[attackerType][targetType]` effectiveness matrix is also now located**, immediately after the unit-type table in the DAT file — see [combat-type-effectiveness-matrix.md](reports/combat-type-effectiveness-matrix.md). All constants for the melee formula are now in hand; what remains is *using* them: simulate the full recorded battle in [battle-observation.md](reports/battle-observation.md) and compare exact numbers (this would also resolve the matrix's remaining attacker/defender axis ambiguity). Still separately open: the uniform ~2.7% whole-army loss from [field-recruitment-uniform-attrition-and-fleet-drift.md](reports/field-recruitment-uniform-attrition-and-fleet-drift.md) (still unclear whether that's the same mechanic as per-engagement combat or a distinct occupation/attrition pass); captured spoils; and the unexplained 9→2 morale swing with no recorded combat.
5. [x] **City capture/allegiance/loyalty resolution. Done — confirms nearly every save-diffing finding.** Found via a new technique: Ghidra's reference analysis doesn't find these string xrefs at all (a real tooling gap — see below), so the whole application range (1,881 functions) was decompiled to one file and grepped for string literals directly, finding `"falls to"` immediately. Siege outcome = `attackerStrength (per-unit sum, archers tripled) > defenderStrength (fortification×150 + loyalty×250 + ... , −20% if owner≠allegiance)`. Ownership transfer updates unity (+9/−15, asymmetric), wealth (±fortification×3000), city count (±1), and **the exact `nationTaxBase` field already solved to 2,440 for Rome** (±per-army-value×4) — ties the tax formula and capture mechanic together. Loyalty rule exactly matches the Taurasia same-turn defect-then-reconquer finding (pulled toward 90 if allegiance==new owner, toward a 40 floor otherwise). Garrison at the captured city is explicitly cleared. See [decompiled-city-capture-resolution.md](reports/decompiled-city-capture-resolution.md). **Update: `FUN_0044ba1c` decompiled — it's not a loss formula, it's a cascading defection mechanic.** After a capture, every other city sharing the just-captured city's previous owner, within 10 tiles of the attacking army, weakly defended and low-loyalty, can automatically defect (`FUN_0044bed8`) with no battle — very plausibly the mechanism behind every "X defects to Y" event seen in this project's saves. `FUN_0044bed8` never touches population/fortification, exactly matching the Modena defection's empirical signature, and revealed a "nation eliminated" cascade when a losing nation's city count hits 0 (not decompiled in depth). Population/fortification loss instead traces to two functions called on *every* attack attempt regardless of outcome inside the siege function itself: army casualties (`FUN_0044ae20`) and a smoothing/decay adjustment to three city-stat fields (`FUN_0044b230`) — meaning the loss seen at a successful capture may be accumulated across however many attempts preceded it, not a one-time capture penalty. See [decompiled-defection-and-siege-attrition.md](reports/decompiled-defection-and-siege-attrition.md). Still open: which city-stat field is fortification vs. population, the exact smoothing formula, and the Felsina screenshot anomaly.
6. [x] **DAT/SAV I/O routines — done, the strongest confirmation this project has produced.** `TPremierForm_OpenGameFile`/`SaveGameFile(As)` were already in the recovered RTTI symbol list — no string search needed. Tracing forward reached a matched read/write function pair that serializes the entire SAV file in one fixed sequence, confirming byte-count for byte-count: the map, city table stride, army/fleet/nation record lengths, and **the mercenary table's 50-slot capacity directly in code** (previously only established empirically). Found a brand-new, previously unknown 61-byte count-prefixed record type in the "unidentified bytes" region, and a **battle-in-progress code path** with an extra block of tactical state — real in the code, but the user confirms saving mid-battle isn't possible in the game, so no real save file will ever exercise it; every save's length is fully accounted for without considering this branch. See [decompiled-sav-file-layout.md](reports/decompiled-sav-file-layout.md). Open: the 61-byte record's identity, a ~6-byte reconciliation gap against the previously-measured 3,042-byte region size, and the fleet-record owner code / city-unit `StateCode` questions are unaffected by this (not covered by this specific function).
7. **`TToEndTurn` — turn/season/quarter sequencing.** Cross-check: week resets to 1 after week 11 at both observed season boundaries; the "51 quarterly" mercenary upkeep and "quarterly" recruitment costs need a real quarter boundary in-code to explain when they're actually charged.

## Explicitly out of scope for this pass

- Full AI opponent strategy — the roadmap's own scope decision favors faithful *rules* with a redesigned interface/AI, not a byte-for-byte AI port; only decode enough of `ComputerGeneral` to understand war/peace/recruit triggers if it falls out cheaply from the combat work above.
- Victory conditions — no current urgency.
- Tactical battle grid rendering and other UI-only code.

## Method, per target

1. Locate the form/procedure the same way prior reports did: Delphi RTTI method-name tables, the `TMainMenu`/form-adjacent streams, or a literal-string cross-reference (e.g. searching for dialog text like "quarterly", "Current tax", "New income") to find the owning code.
2. Decompile with a Ghidra headless script exporting C-like pseudocode for that function and its immediate callees to a text file.
3. Read the pseudocode and translate it to a plain-language rule, citing the function address(es) — same evidentiary standard as every existing report (`docs/reports/*.md`), which already cite save offsets and screenshot values this way.
4. Check the recovered formula against the empirical numbers listed above. State explicitly whether it matches, and if not, say so rather than adjusting the empirical reading to fit.
5. Write a new `docs/reports/*.md` and update `IC2.Data` doc comments / `docs/roadmap.md` only once a formula is actually confirmed this way — candidate/unconfirmed decompiled readings get the same "candidate" language already used throughout this project.
