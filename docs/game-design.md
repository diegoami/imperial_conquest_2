# Game design: a moddable reimplementation of Imperial Conquest 2

This is a **design document, not an implementation plan**. It translates everything confirmed in `docs/roadmap.md`, `docs/decompilation-plan.md`, and the 40+ reports in `docs/reports/` into a concrete design for a new game, fills the gaps the reverse-engineering left open with explicit, documented creative decisions, and lays out how the actual build phase should run once this is agreed. Four scope decisions were made explicitly with the user before writing this:

1. **Multiplayer**: single-player plus **local hotseat** (multiple humans, one machine, turns in sequence). No networked multiplayer for now, but nothing here forecloses it later (see "Determinism" below).
2. **Maps**: **arbitrary custom maps from day one**, not just the original's 320×140 grid. The original's actual map/nations/cities becomes one *shipped* world definition among possibly many, not a hardcoded assumption.
3. **Battles**: **the original's two battle models, both ported** (revised for v0.6.0 *Battles* by the user's decisions of 2026-10-03 and 2026-10-04, [#496](https://github.com/diegoami/imperial_conquest_2/issues/496); this principle first said "instant abstracted auto-resolve, no tactical grid"). A field battle in which **no human seat** takes part, every siege and every naval battle is resolved in one shot by the original's own **instant resolver** (Combat). A field battle between two armies with a **human seat on either side** opens the original's **tactical battle**: a 14 × 12 grid, placement, alternating half-rounds, shooting, melee, morale, rout and surrender, played by the human and by the original's own computer general. It is a fresh port of the decompiled `TBattleMap`, rule for rule (Combat, "The tactical battle"). The original's per-exchange pacing delay is **not a bug**: it is a `GetTickCount` busy-wait whose duration is a *stored per-nation player preference*, with its own `TBattleDelays` settings dialog, and it can be set to zero from inside the original game **[confirmed: battle-freeze-diagnosed-procmon.md]**. It reads as a freeze only because a busy-wait never returns to the message pump. So pacing belongs to the battle screen, never to the combat rules or the game state: the port's rules run without waiting, and the screen may pause between exchanges for display, by a display-only player setting whose default is 0 s (the user's decisions of 2026-10-04 on [#496](https://github.com/diegoami/imperial_conquest_2/issues/496)).
4. **Build process**: once this design is settled, implementation should proceed in **large autonomous chunks** (see "The build harness" at the end), not small human-reviewed increments.

Every rule below is tagged **[confirmed]** (has direct RE evidence, cited), **[derived]** (a reasonable extrapolation from confirmed data, e.g. filling in a formula's shape where only some constants were pinned down), or **[designed]** (no RE evidence exists or it was intentionally left out of scope; this is new game design). Nothing is presented as RE'd when it isn't.

> **Read [design-audit.md](design-audit.md) alongside this document.** A systematic audit found several whole subsystems this design was silent on (naval transport and naval combat, fleet condition and repair, supply as a purchased economy with per-army money purses, city fortification orders, army/unit management) and corrected four sections that were written on assumptions rather than evidence (Movement, Recruitment's mercenary claims, Diplomacy, Victory conditions — all fixed in place below). **All ten of its open questions are answered by the user and folded in here**: the auto-resolve uses the original's own instant battle resolver (Q1); naval is in scope for the first playable version (Q2); and Q3 (diplomacy fidelity), Q5 (default victory condition), Q6 (human/AI asymmetries) and Q8 (bug-reproduction policy) are all answered the same way — **ship both `classical-faithful` and `improved` as named, user-selectable rulesets**, surfaced as a prominent choice at New Game rather than buried in scenario JSON (see "Ruleset format" and "User interface" below). The milestone list at the end has been revised for all of it. Q4 (per-army purses) is folded into the same two-preset table. Q7 (city-orders extensibility) is answered independently — ship a generic, data-driven `cityOrders` table with fortify as the only shipped entry. Q9 (supply purchase) is answered from the user's own play: resupplying at your own cities is free, buying at anyone else's costs money, in both presets. Q10 (does the rout mechanic change `combat.onDefeat`) is answered: no change.

## Design principles

These are the load-bearing decisions everything else follows from:

1. **Data over code, wherever the cost is reasonable.** Every gameplay *constant* (unit stats, cost tables, tax rates, caps, thresholds) lives in external data (JSON), not hardcoded in engine source. Formula *shape* (the actual arithmetic — `tax = base × rate / 100`) stays as tested engine code, not a scripting language. A full expression-scripting system was considered and rejected: it would let scenario authors change formula shape too, but it's a lot of engineering and testing surface for a one-developer(+agent) project, and "change the numbers" covers the overwhelming majority of real modding use cases. If a future scenario genuinely needs different formula shape, that's a new `Ruleset` *variant* (a small C# strategy class selected by name in the ruleset data), not a scripting engine.
2. **The original's confirmed rules are the default ruleset**, not *the* rules. A `Ruleset` is a named, versioned bundle of the constants and formula variants above. The game ships with a `"classical-faithful"` ruleset built from everything in `docs/reports/`. Anyone (including future-me, building this) can add another ruleset without touching the engine.
3. **World layout and ruleset are separate axes.** A `World` (map + starting nations/cities/units) and a `Ruleset` (the numbers/formulas governing play) are independent, swappable pieces. A `Scenario` combines one of each plus victory conditions and player/AI assignments. This is what "leave open the possibility of creating custom scenarios" means concretely — see "The scenario system" below.
4. **Determinism first.** All randomness goes through one seeded RNG service threaded through the turn coordinator. This is required for reproducible tests, for eventually adding network multiplayer without a rewrite (lockstep-style: ship commands + seed, not state), and — practically — for an autonomous build loop to write hard assertions instead of "looks right."
5. **Assets are abstract references, resolved by a pluggable pack.** Engine and rules code never touch a file path or a specific `.wav`/`.png`; they reference stable keys (`unit.archers.icon`, `sfx.city_captured`). See "Asset packs" below.
6. **Original source files remain read-only; compatible SAV export is a separate operation.** The user's planned 0.7.x request on [#1191](https://github.com/diegoami/imperial_conquest_2/issues/1191) supersedes the earlier one-way-only policy. Native Save stays JSON. [T184](tasks/T184.md)–[T186](tasks/T186.md) add original-compatible export for validated classical-faithful strategic states through an immutable private SAV template, with explicit representation limits, no overwrite and original-game validation; see "Original-save compatibility."

## The core data model

Four kinds of data, loaded independently:

```
World       = terrain grid (W×H, arbitrary) + city list + nation list + starting armies/fleets/units
Ruleset     = named bundle of constants, cost tables, and formula-variant selectors
Scenario    = a World + a Ruleset + victory conditions + player/AI seat assignments + (optional) turn limit
SaveGame    = a live, versioned snapshot of a Scenario in progress (includes which World/Ruleset it started from)
```

`World` is the generalization of everything `IC2.Data` already parses from the DAT/SAV files — it's the same information (map cells, cities, nations, starting armies), just no longer assumed to be exactly 320×140 with exactly 16 nations and exactly 334 cities. The original's actual data becomes **one shipped `World`** (working name: `classical-mediterranean`), produced by a one-time export tool built on top of the existing `IC2.Data` parsers — not a runtime dependency on the user owning original files. (Importing an actual original `.sav` remains a separate, ongoing feature — see below — distinct from using the *default world* to start a fresh game.)

### World format (sketch, JSON)

```json
{
  "id": "classical-mediterranean",
  "width": 320, "height": 140,
  "terrain": "base64-or-run-length-encoded tile-id grid",
  "tileTypes": ["plain", "forest", "mountain", "river", "water", "..."],
  "cities": [ { "id": 0, "name": "Rome", "x": 95, "y": 28, "owner": "rome", "population": 220, "fortification": 60, "..." } ],
  "nations": [ { "id": "rome", "name": "Rome", "color": "#c62828", "capital": 0 } ],
  "startingUnits": [ /* armies, fleets per nation */ ]
}
```

Tile types are an open, extensible list — not fixed to the original's 12 terrain codes / 6 distinct terrain names **[confirmed: terrain-move-cost-table-in-dat.md; the earlier "5 values" figure was how many had been matched to screenshots in rivers-and-map-markers.md, not how many exist]** — a custom world can define new ones (a ruleset/renderer just needs matching movement-cost and art-key entries for whatever it defines).

### Ruleset format (sketch)

```json
{
  "id": "classical-faithful",
  "unitTypes": [ { "id": "light_infantry", "moves": 4, "battalionSize": 5000, "shots": 0, "range": 0, "recruitCost": 12 } ],
  "typeEffectiveness": "5x5 melee matrix, DAT 0x1F7A6, [confirmed: 2026-10-04-decompiled-tactical-battle-rules.md §5]",
  "economy": { "taxFormula": "base*rate/100", "quarterlyUpkeepPerShip": 3, "recruitCostFormula": "(troops/200)*priceTable[type]" },
  "combat": { "onDefeat": "destroy", "meleeLossCapPercent": 40, "shootingRangeFormula": "...", "qualityPromotion": { "floorTier": "average", "furtherPromotionChance": "1 in 4", "capTier": "elite" } },
  "diplomacy": { "...": "see Diplomacy section, all [designed]" },
  "victoryDefaults": { "...": "see Victory conditions section" }
}
```

Every numeric table here has a direct citation to a report in `docs/reports/` or is explicitly marked `[designed]` inside the file's own comments/docs (JSON doesn't support comments natively — use a sibling `.md` per ruleset explaining provenance, or a `"_provenance"` key per field).

## Subsystem-by-subsystem design

### Calendar and turns — **[confirmed]**

Week `+2 mod 12` per turn cycle, season advances at the 11→1 wrap, year decrements at the Winter→Spring wrap, quarterly billing on the season boundary. Directly reuse the confirmed calendar model from [`decompiled-turn-and-calendar-sequencing.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-turn-and-calendar-sequencing.md) and [`decompiled-quarterly-billing-and-economy.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-quarterly-billing-and-economy.md), but read both with their later corrections. The weekly city loop the first calls "population growth" is **city supply production**, and the second's "unity decays by 3" is mobilization's ([`city-population-growth.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/city-population-growth.md); both under Economy below). This subsystem needs no new design — it's ready to implement as-is, parameterized only by "weeks per season" / "seasons per year" in the ruleset in case a custom ruleset ever wants a different calendar (unlikely to be exercised, cheap to support).

**Hotseat turn model** — **[designed]**: sequential per-nation turns within one calendar tick, exactly like the original's single-active-nation model (`TPremierForm`'s active-nation field) **[confirmed structurally by the SAV trailer's active-nation field and turn-order table]**, just with human-controlled seats pausing for local input instead of dispatching to AI. Run with two human seats, the original works this way: the AI seats between the two humans play by themselves, End turn hands control to the next human seat in the order, and the calendar advances once a round, at the round tick **[Wine candidate: [`2026-10-02-two-human-seats.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-02-two-human-seats.md)]**. New Game shuffles the turn order: starting from the DAT's nation order, it swaps each slot `i = 0 … 15` in turn with the slot `Random(16)` picks. That is not a Fisher–Yates shuffle, so the 16! orders are not equally likely. The order then stays fixed for the whole game, an eliminated nation keeps its slot, and the human's choice of nation does not change it **[confirmed: code, [`2026-10-03-new-game-turn-order-shuffle.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-03-new-game-turn-order-shuffle.md); it reproduces the observed order for seed 12345 and the saved orders of two clock-seeded desktop games]** ([`investigations/dat-file-layout.md`](investigations/dat-file-layout.md)). With the seed fixed, the order is the same whoever is human, so a nation's first turn starts on the world as the AI seats before it have left it **[Wine candidate: [`2026-10-02-start-as-each-nation.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-02-start-as-each-nation.md)]**; the leaders-form plays confirm it directly — two-, six- and sixteen-human tick patterns of one seed all drew the same order, and the first ticked human in that order played first **[confirmed in play: [`2026-10-06-leaders-form.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-06-leaders-form.md) T05–T06, W07; Wine-only]**. The clone also plays those earlier AI seats before the first human turn (`GameSession.AdvanceToHumanSeat`), but its turn order is the world file's fixed default, the DAT's nation order with Rome first, not a shuffle [designed: the `turnOrder` provenance in `data/worlds/classical-mediterranean.json`]. The presets differ here: `classical-faithful` shuffles the turn order from the scenario seed at New Game, as the original does, and `improved` keeps the fixed default, so its start is predictable [designed: the user's decision of 2026-10-02]. The faithful shuffle uses the original's algorithm on the clone's own random generator, so a given seed does not give the original's order for that seed [designed: the user's decision of 2026-10-03]. With two or more human seats, any autosave the clone keeps is one file per human seat; the original's shared name, which lets the second human's autosave overwrite the first's, is not reproduced [designed: the user's decision of 2026-10-02]. A battle between an AI seat and a human seat during the AI phase stays resolved at once (option A); its result is shown to that human in the battle-result window when their next turn starts [designed: the user's decision of 2026-10-02]. Under `HumanBattles = Tactical` (v0.6.0), the clone instead does what the original does: it opens the tactical battle for that human during the AI phase (the user's decisions of 2026-10-04 on [#496](https://github.com/diegoami/imperial_conquest_2/issues/496); Combat, "The tactical battle"). Between human turns, an optional "pass the device" confirmation screen hides the previous player's info before the next human's turn starts (toggle per scenario — off by default for a fast local game between people who don't mind, on by default if a scenario explicitly marks itself "blind hotseat").

### Economy — **[confirmed, ready to implement directly]**

- Tax: `income = nationTaxBase × taxRate / 100` **[confirmed: decompiled-fleet-tax-and-mercenary-formulas.md, decompiled-quarterly-billing-and-economy.md]**. A computer seat rewrites its own rate once a season, in the season's last week (week 11 — at save granularity the write is already in the week-11 save, with the week-11 → new-season transition (the quarterly tick itself) carrying no write), in this order: `tax = max(5, tax − 6)` when unity is under 650 or the treasury is above `wealth/2000`; then `tax = min(40, tax + 9)` when the treasury is negative, or the nation is threatened and holds under 1,000; then `tax = 0` when the treasury is positive and unity is under 500 — the same `+0x44A` field the human's slider writes **[confirmed: decompile, [`2026-10-07-strategic-ai-turn.md`](https://github.com/diegoami/imperial_conquest_2-research/blob/main/docs/reports/2026-10-07-strategic-ai-turn.md) §2.3; fifteen in-play evaluations, both clamps and the cut-then-raise double fire, [`2026-10-07-ptolemy-run-between-turn-sweep.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-07-ptolemy-run-between-turn-sweep.md) §4; placement correction (week-11 save, not the quarterly tick) and 18/18 decidable rows matched, 0 mismatches, [`2026-10-07-ai-turn-corroboration.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-07-ai-turn-corroboration.md) §1]**.
- Quarterly upkeep ([`upkeep-payment-and-desertion.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/upkeep-payment-and-desertion.md)). The **treasury** pays regular units and garrison slots, `(troops / 200) × price`, and launched ships, `3 × ships`; a fleet still under construction is not billed, although the original's Balance sheet Fleet line counts it, so that line overstates the next bill by 3 per ship being built **[confirmed: code (`owner ≥ 0` and countdown −1) and a paired Wine run in which the quarter moved Rome's treasury by +23 both with and without a 50-ship fleet on order: [manual consolidation](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-22-manual133-contradictions-consolidated.md) item 12]**. It never checks the balance, so it can go into debt. Each army's **own purse** pays its mercenaries, `((troops / 200) × price × quality) / 5` **[confirmed: the human nation's whole-quarter treasury change, 6 of 6]**. **Non-payment**: a mercenary unit reached with its army's purse at or below zero deserts as a whole unit, taking its share of supplies (`troops / 100`) — the original's only unguarded supplies subtraction. The last payment can overdraw the purse and the deserter's carry-off the supplies, both only inside the loop: it floors each of the purse and the supplies at 0 before leaving the army, so neither field is ever persisted negative. Regulars never desert, and there is no morale loss or message **[confirmed: 1 desertion, Rome in debt with every regular intact; the gate, the floors and the carry-off: decompile, `upkeep-payment-and-desertion.md` (2026-10-07 extension), `2026-10-07-army-supplies-and-money-signedness.md`]**. Each deserter's slot is filled by the army's last unit, which the loop then skips, so an unpaid all-mercenary army of `n` units loses `⌈n/2⌉` of them a quarter, chosen by slot position, and the quarter that takes its last unit deletes the army **[confirmed: decompile, `upkeep-payment-and-desertion.md`; seen once in play — 7 units, 4 deserted and the 3 the slot rule predicts survived, and a one-unit army was deleted at once: [`2026-10-09-turn-end-and-ai-army-removals-restore-their-tile.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-turn-end-and-ai-army-removals-restore-their-tile.md), research `e6b4643`]**. Played on staged mercenaries at a purse of 0: the unit left with `troops / 100` of supplies (170 → 87, against 117 in the control), with no news, and of two mercenaries the second, moved into the first's slot, stayed that quarter **[confirmed: Wine, staged units; [`2026-10-12-g3-original-checks.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-12-g3-original-checks.md), research `c313b8e`, §1d]**. **Debt** (treasury below `−wealth / 500` or −20,000, or unity under 400) **[derived: decompile, `FUN_00452034` :55034–55036; the threshold was not re-read by [`2026-10-05-end-of-game-screens.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-05-end-of-game-screens.md)]**; the treasury bound is the unrounded `wealth / 500`, not the Balance sheet's rounded *Debt limit*: at wealth 2,577,000 (5,154, shown as 5,000) a human treasury of −5,100 was not deposed and −5,200 was **[confirmed: Wine, staged treasury, paired runs in one process; [`2026-10-11-g1-original-checks.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-11-g1-original-checks.md), research `89c37ff`, G2]** risks deposition: an AI nation has a 1-in-9 chance each quarter, which resets its treasury and props up its unity **[confirmed: 2 of 15 in run-1-rome; two more debt depositions at quarter ticks, Gaul and Celtiberia, both with the treasury zeroed and the `max(unity, min(550, unity + 150))` reset, [`2026-10-07-ptolemy-run-between-turn-sweep.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-07-ptolemy-run-between-turn-sweep.md) §6]**. The AI's test has the same disjuncts, so unity under 400 deposes a solvent nation too, and the unity reset is applied after the nation's ordinary quarterly unity update: 32 of 312 staged debtor trials were deposed (1 in 9), and a solvent nation at unity 350 was deposed in 2 of 12, its unity 373 after the update becoming 523 **[confirmed: Wine, staged; [`2026-10-12-g3-original-checks.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-12-g3-original-checks.md), research `c313b8e`, §1f]**; a human nation is deposed at the start of its turn, before any order, when it is in debt, its unity is under 400, it holds all 334 cities, or the year reaches 250 BC (`FUN_00452034`). ### Combat — **[confirmed: the original's two battle models — its instant resolver, ported, and its tactical battle, decompiled statically, for v0.6.0]**

The original has two battle models, and the clone ports both. An army attacking an army (`FUN_0044AEE4`) sets the attacker's moves to 0 and then, **if both nations are computer-controlled**, resolves the battle in one shot with the instant resolver below; **otherwise it opens the tactical battle** (`TPremierForm_StartBattle`, the `TBattleMap` screen) **[confirmed: code: [`decompiled-diplomacy-peace-terms-and-instant-battles.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-diplomacy-peace-terms-and-instant-battles.md) §"The original's instant battle resolver"]**. Sieges and naval battles never open it: they are always instant **[confirmed: code, static: [`2026-10-04-decompiled-tactical-battle-rules.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-04-decompiled-tactical-battle-rules.md) §Answer, a whole-`CODE` scan of the calls]**. The instant resolver is specified first; the tactical battle has its own subsection after it.

- **Two morales, not one — do not merge them.** The **strategic army morale** is army record `+14`, a direct multiplier in the power formulas below **[confirmed: decompiled-unit-map-orders-and-record-fields.md]**. The **per-unit tactical morale** is a separate runtime array that the `±2`/`−3`-per-exchange rule operates on **[confirmed: battle-quality-promotion-and-morale-array-decompiled.md]**. The rule compares the fraction of troops each side lost, not power: the side with the smaller `troops div loss` (the larger fraction lost) takes `−3` and the other `+2`, ties against the attacker, both capped at 99 with no floor **[confirmed: code, static, not yet checked in play: [`2026-10-04-decompiled-tactical-battle-rules.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-04-decompiled-tactical-battle-rules.md) §5–6; it corrects `decompiled-combat-formula-structure.md`'s "better power ratio"]**. The instant resolver uses only the first; the tactical battle uses both. They were conflated in earlier drafts because one report called `+14` "army experience". Two more facts tie them together in the original; both belong to the tactical battle (below), and neither reaches the instant resolver. First, on entry to a **tactical** battle, a side whose own nation is **computer-controlled** gets `+3` to its strategic `+14`. The write is persisted, unclamped and made once per battle, and the human side gets nothing. The instant path never writes `+14`. - **The rout mechanic — the tactical battle's, not the instant resolver's [confirmed: battle-replayed-rout-mechanic-and-combat-constants.md].** `FUN_00438fb0` is called on both participants after every melee exchange and on the target after every shot: a unit is removed outright when its troops fall below its type's `standardBattalionSize / 25` (light inf 600 · heavy inf 240 · archers 140 · light cav 280 · heavy cav 100), when its tactical morale is ≤ 19, or on a `Random(m) + Random(m) ≤ 29` check in the 20…39 band — and each rout then costs every surviving friendly unit 6 morale and drags anyone below 30 out with it, while handing every live enemy +5. The cascade is **one level deep**: a unit it drags out starts no cascade of its own and earns the enemy no +5 **[confirmed: same report, consequence 3, corrected in research `eb1c886`; it first said "recursively"]**. Apart from a surrender, which removes all of the surrendering side's units at once with no cascade and ends the battle **[confirmed: code, static: [`2026-10-04-decompiled-tactical-battle-rules.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-04-decompiled-tactical-battle-rules.md) §6]**, this is **the only way a unit leaves a tactical battle**: both loss caps are 40% of the side's own troops, so attrition alone can only asymptote toward 1. It supersedes the `0.6ⁿ`-compounding explanation an earlier report gave for units being wiped. The instant resolver never needs it: it annihilates the loser wholesale, and its only per-unit removal is a different rule, the small-unit deletion in the resolver block below. The tactical battle takes the rule verbatim, as the whole-module decompile reads it (the tactical battle's "Morale and rout", below). - **What's redesigned — decided (audit Q1): use the original's own instant resolver.** An earlier draft of this section proposed running the tactical exchange math headlessly with an invented `"pairing"` rule, on the stated grounds that "the original's own placement-driven pairing doesn't translate to an instant-resolve model".
```text
armyPower(a)  = ( Σ_units powerWeight[type] × troops / 100 ) / 80 × armyMorale
fleetPower(f) = base + random(4) × (base / 10)       (integer: base / 10 truncated first)
                base = ships × condition / 10 + (carriedArmy ? siegeStrength(army)/50 : 0)

field battle   winner = higher armyPower, ties to the defender
               loser's army destroyed outright
               winner casualties  = applyLosses(loserPower × 40 / winnerPower)
                 ratio ≤ 40: the weaker power × 40 / the stronger, 40 only at a tie
                 per unit: troops −= troops / (Random(15) + 105) × ratio
                 then every unit left below standardBattalionSize / 10 (national)
                 or / 5 (mercenary) is deleted, before the promotion roll
               winner absorbs loser's money and supplies (supplies capped at troops/100)
               every surviving unit: quality = max(quality, average); 1-in-4 → quality + 1 (cap elite)
               unity: loser −25, winner +25 (cap 990)
               2-in-5 chance of an automatic peace treaty if loser unity > 500 and cities > 7;
               with a human side, also only if the winner's army strength < the loser's, the
               draw taken last, and the treaty is only offered: it needs the human's Yes

siege          atk = siegeStrength(army) = Σ(troops, archers × 3) / 80 × armyMorale
               def = defenderStrength(city), × 9/10 if the army's nation is the city's allegiance
               on every attempt, win or lose, before the outcome test:
                 the city's pending fortification order is discarded; loyalty, fortification and
                 population erode (City capture section above); population floored at maxPop / 6 + 1
                 the attacker takes applyLosses(max(1, min(15, def × 6 / atk)))   (with its deletion pass)
               attacker wins only if atk > def (ties to the defender); the city's troops take no casualties

naval battle   winner = higher fleetPower, ties to the defender; loser's fleet (and any army
               aboard it) destroyed; unity ± floor(loserShips / 2)
               winner damage, FUN_0044B4F8(winner, loserPower, winnerPower):
                 r = max(1, loserPower × 100 / winnerPower);  d = r² / 100          (0 … 100)
                 ships −= ships × d / 300;  condition −= condition × d / 300
                 a carried army takes applyLosses(d); if it still exists and d > 70, it also
                 loses unitCount × d / 250 + 1 random units, counted after applyLosses and each
                 removed swap-with-last
```

#### The defeated side's fate — `combat.onDefeat`, `classical-faithful` vs `improved` — **[designed, new]**

The original always annihilates the loser (`classical-faithful`, verbatim, as above). The instant path has no fighting retreat, which reads as unusually harsh for a game whose auto-resolve runs constantly rather than occasionally — so the `improved` ruleset changes what happens to the losing **field-battle and naval-battle** side, without touching the confirmed math for who wins or how many casualties the winner takes:

- The loser's army/fleet **survives at reduced strength** instead of being destroyed: apply the same `loserPower × 40 / winnerPower`-shaped casualty formula to the loser's own troops (mirrored, not the winner's number), rather than zeroing it out. Exact ratio is ruleset data, defaulting to the winner's own cap, tagged `_provenance: "designed, no original analogue — the original has no partial-defeat outcome to measure"`.
- The survivors **scatter**: relocated 2–4 tiles (ruleset data, `combat.improvedDefeat.scatterTiles`) from the battle site, in a direction away from the victor, onto the nearest valid tile of the right kind for that army/fleet (passable land for an army, sea for a fleet) that is not occupied by another army/fleet/city. If no valid tile exists at the target distance, shrink the distance one tile at a time down to 1; if even an adjacent tile is unavailable (fully boxed in), fall back to the `classical-faithful` outcome — destroyed — because there is nowhere to route it, and that is a corner case worth a named test rather than a silent crash.
- The scattered army/fleet's **moves are zeroed for the rest of the turn it lost on**, exactly like the existing (currently AI-only, `classical-faithful`) blocked-step rule, generalized here to whichever seat just lost. This, combined with the fact that the **victor's own move for that turn was already spent issuing the attack**, is what stops "the other army, which would not be able to catch it immediately" — nobody gets a free second action to pursue in the same turn. Catching a routed army is a *following-turn* decision, made with normal moves against a normal, visible map marker; nothing hides it.
- Money and supplies: unchanged from the confirmed formula — the winner still absorbs them (a scattered army leaves its baggage behind exactly as a destroyed one does); only the troops' fate differs.
- Unity: same ±25 swing as `classical-faithful`, since that reflects the *battle's* outcome, not the survivors' fate.
- **Siege is explicitly out of scope for this flag.** A city garrison has nowhere to scatter to — it is defending its home — so sieges keep the existing capture/defection model regardless of `combat.onDefeat`. This flag only ever touches the field-battle and naval-battle variants of the instant resolver.
- **After a tactical battle**, `improved` scatters the loser's surviving remnant by the same rule, after its retreat losses (the tactical battle's "What `improved` changes", below; the user's decisions of 2026-10-04 on [#496](https://github.com/diegoami/imperial_conquest_2/issues/496)).

**The board and the battle state** (report §1).

- **The board** is 14 × 12 cells, `x` 0–13 and `y` 0–11, with no terrain: no impassable cell, no movement cost and no modifier, and the module never reads the strategic map. Distance is Chebyshev, `max(|dx|, |dy|)`, and adjacent means distance 1.
- **A unit** is one of the army's 20 unit slots. Battle slots 0–19 are the attacker's and 20–39 the defender's. Each holds its position; its origin (national, or a mercenary label used only for display and written back); its type; its troops (0 means out of the battle); its quality (constant during the battle); its battle morale; its moves left this half-round; its shots left for the whole battle (initially the type's stat: light infantry 7, heavy infantry 0, archers 25, light cavalry 9, heavy cavalry 0); its melee target (a slot, or none); and its name.
- **A cell holds an icon code, not a slot**: empty, or `type × 3 + size` for the attacker and the same `+ 20` for the defender, where `size = min(2, troops div (standardBattalionSize div 3))`, recomputed after every loss. Read from the running game's screen, the size changes at exactly `std div 3` and `2 × (std div 3)` troops, on both sides, to the troop: light infantry 5,000 and 10,000, heavy infantry 2,000 and 4,000, archers 1,166 and 2,332, light cavalry 2,333 and 4,666, heavy cavalry 833 and 1,666; the 30 (type, side, size) combinations draw 30 distinct images **[Wine candidate: sweep, B8]**. The unit at a cell is found by scanning the 40 slots for a live unit at that position; when two units share a cell, the last one in the scan wins. The lookup reads only the slots; the grid code at the cell is never consulted **[confirmed: code, static, [`2026-10-21-crafted-battle-grid-movement-and-line.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-21-crafted-battle-grid-movement-and-line.md) (research `1c203b7`)]**.
- **The rest of the state** is the attacker army, the defender army, the side to move (0 attacker, 1 defender), whether placement has finished, and a half-round counter. With the slots and the grid, this is the original's battle block, saved after its battle flag ([`decompiled-sav-file-layout.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-sav-file-layout.md), corrected in research `b5db496`). The sweep decoded the same block from the saves independently, field by field: 2,105 bytes after the flag (9 header bytes, 40 slots of 44 bytes, the 14 × 12 icon grid), read from 585 saves, with the icon code equal to the rule above in 567 of them and the other 18 exactly the crafted saves that edit the grid **[Wine candidate: sweep, B2 and its review notes]**. It also shows that the game plays from the slots and never repairs the grid: a stale or doubled cell persists **[Wine candidate: sweep, B3]**. The code shows why: movement and human placement carry the stored code from cell to cell and write empty behind them, and nothing recomputes a moved unit's code **[confirmed: code, static, [`2026-10-21-crafted-battle-grid-movement-and-line.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-21-crafted-battle-grid-movement-and-line.md) (research `1c203b7`)]**.

**Copy-in** (`FUN_00437DE4`, a fresh battle only; report §2).

1. For each side whose nation is computer-controlled:
   - its **strategic** army morale `+14` goes up by 3, unclamped, and the change persists in the army record. The hook saw it in the copy-in draws of 315 staged battles: with both armies saved at morale 65, Gaul's (a computer nation) copy-in base was 68 and Rome's (a human nation under *Computer general*) 65, so *Computer general* does not earn the `+3` **[Wine candidate: hook]**;
   - its army's 20 unit records are selection-sorted, descending, in place, by `troops × M[type][0] div M[0][type]` (light infantry ×1, heavy infantry ×15, archers ×0.5, light cavalry ×5, heavy cavalry ×6, in integers), with `i = 0 … 18`, `j = i + 1 … 19`, a strict `>` and whole-record swaps. The order persists in the army and is the computer general's iteration order. The sweep saw Gaul's five units re-sorted heavy infantry first at the start, and the human side's units left in their army order **[Wine candidate: sweep, B2]**;
   - its nation adopts the opponent's two pause settings. These are display settings, and the clone keeps no state for them.
2. Every cell is emptied and every slot's troops set to 0. Copy-in does not write the melee-target word. At the recorded fresh-battle boundary, attacker targets remain 0 in occupied and unused slots until that side's first setup; the defender's initial setup has already cleared all its targets to −1 **[code: `FUN_00437DE4`, `FUN_00439968`; Wine candidate: T129's 323 fresh-series snapshots, verified by T173]**. Resume does not apply fresh-copy target initialisation.
3. For each attacker unit slot `s = 0 … 19` with troops > 0, in order: position `(s mod 13, s div 13)`; origin, type, troops, quality and name copied; shots from the type's stat; and `morale = max(60, min(90, Random(quality × 4) + armyMorale))`, where `armyMorale` is the strategic `+14` after any `+3`. The hook found one `Random(quality × 4)` per live slot, attacker then defender, and this clamp, in all 315 staged battles **[Wine candidate: hook]**.
4. The same for the defender, at `(s mod 13, 11 − s div 13)`. The saves show the shots starting at 7, 0, 25, 9 and 0 and the battle morale between 60 and 99 **[Wine candidate: sweep, B2]**.
5. The battle flag is set, the side to move is the defender, the counter is 0, and the first half-round is set up.

**Placement** (report §2, §3). The defender places first (half-round 1) and the attacker second (half-round 2); then the attacker moves first (half-round 3). A human places by clicking an own unit and then an empty cell in its home rows, `y < 3` for the attacker and `y > 8` for the defender, as often as it likes during its placement half-round; a unit not moved keeps its copy-in position. A human placement moves the code stored in the unit's old cell to the new cell and writes empty into the old one (`FUN_004375EC`) **[confirmed: code, static, [`2026-10-21-crafted-battle-grid-movement-and-line.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-21-crafted-battle-grid-movement-and-line.md) (research `1c203b7`)]**. A computer side places by formation (the computer general, below). The sweep saw the defender placed first, the attacker second, then the sides alternating with the attacker first **[Wine candidate: sweep, B4]**; a position edited into a save during placement is overwritten when the computer re-places **[Wine candidate: sweep, B3]**.

**The half-round** (report §3). There is no initiative stat: the sides alternate.

- **Setup** (`FUN_00439968`, which is also the path a loaded battle resumes through). Let `dmin` be the smallest distance between a live own unit and a live enemy unit. For each of the side's 20 slots, the melee target is cleared and the moves are reset to the type's stat (light infantry 4, heavy infantry 2, archers 4, light cavalry 6, heavy cavalry 5). If its nation is computer-controlled **or its own Computer general flag is on at setup**, the type is not heavy infantry, `dmin > 2` and the counter (read before the increment) is below 10, the moves are 1 instead: the computer's slow advance (the sweep's Gaul light infantry with 1 move is this rule **[Wine candidate: sweep, review notes]**). Then the computer general's 40 target claims are cleared and the counter goes up by 1. There is no placement exemption. A later general toggle preserves the already assigned moves; the next setup reevaluates control **[confirmed: code; Wine timing candidate: [Computer General predicate and reload](https://github.com/diegoami/imperial-conquest-2-research/blob/500e52124c93ca020bd6866071198c4d04210c29/docs/reports/2026-10-16-computer-general-predicate-and-reload.md)]**. Copy-in sorting and strategic morale +3 remain nation-only.
- **End** (`FUN_00439C20`). The phase advances: during placement, side 1 hands to side 0, and side 0 sets "placed" without changing side; afterwards the side toggles. Then the melee of **the side that just moved** is resolved, with the targets it set. If the battle is not over, the next half-round is set up.
- **Who plays it** (`FUN_00439C84`). While the side's nation is computer-controlled, or *Computer general* is on for that side, and the battle is not over, the computer general plays the half-round (placement or movement) and ends it. A human side waits for its orders. *End turn* ends the half-round and hands to that loop. *Computer general* enables the side to move; it is not a symmetric toolbar toggle. A human-side Information-window click is consumed by the general's polling, clears that side's flag and returns control, retaining the current setup's remaining moves. It need not interrupt before the first unit acts; an AI nation remains computer-controlled with general off **[confirmed: code, `0x437ab8`, `FUN_0043a31c` / `FUN_0043abb4`; Wine interruption candidate, [`2026-10-16-computer-general-predicate-and-reload.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/500e521/docs/reports/2026-10-16-computer-general-predicate-and-reload.md)]**.
- **A human's orders** (`OnMapClick`). A left click on an own unit selects it and shows its details. An enemy click can inspect basic details without selecting an enemy for commands: with no friendly selected it keeps selection empty; a distant or actual-zero-move enemy click clears friendly selection, while an eligible adjacent click assigns the target. Enemy quality, morale, moves and shots remain withheld **[confirmed, partial: stock-original Wine; [enemy-click intake](investigations/manual-restrictions-and-gui-evidence.md)]**. A left click on an empty cell with a unit selected places it (during placement) or moves it. A left click on an adjacent enemy, by a unit with at least 1 move, sets that unit's melee target, at no cost in moves. A right click on an enemy, by a unit with shots, moves and the enemy within range, shoots. A right click on an own unit clears its target. Moving a unit clears its target.

**Movement** (`FUN_00438D24`, step `FUN_00438A6C`; report §3).

- The unit walks an 8-connected Bresenham line toward the destination: `err = 2 × minor − major`; while `err ≥ 0`, a minor step and `err −= 2 × major`; then the major step and `err += 2 × minor`. Each step costs one move, and the unit enters the path cell when it is empty. A step copies the code stored in the old cell to the new cell and writes empty into the old cell, so a stale code travels with the unit, and a cell another unit still stands on is left reading empty (`FUN_00438A6C`) **[confirmed: code, static, [`2026-10-21-crafted-battle-grid-movement-and-line.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-21-crafted-battle-grid-movement-and-line.md) (research `1c203b7`)]**.
- When the path cell is blocked, two alternatives are tried: `(px ± 1, py)` along a column, `(px, py ± 1)` along a row, and on a diagonal `(ux + sx, uy)` and `(ux, uy + sy)` from the unit, swapped when `y` is the major axis. A cell costs 1 when it is on the board, empty, and within distance 1 of both the path cursor and the unit, and 10 otherwise. The cheaper alternative is taken when it is cheaper than the path cell, ties going to the first.
- The walk stops when the moves fall below 1, before the computer targeting checks run, when the chosen cost is above 9, or when the path reaches an occupied destination. Spending the last move beside an enemy therefore does not assign a new melee target (T174; `FUN_00438D24` requires positive moves before targeting). If shooting spends the last move inside those checks, the step also stops before changing coordinates or decrementing moves (`FUN_00438A6C`). A human's move is walked a second time when the first walk did not arrive (`MoveHumanUnit`).
- **For a side driven by its computer nation or its own Computer general flag**: a unit with a target does not move; before spending its **last** move, a unit gives it up (moves become 0) when the 3 × 3 around the next path cell holds an enemy at least as strong as itself, by `S = (troops × quality div 100) × morale × M[mine][theirs]`; and each step first checks two things. If the unit is adjacent to the enemy at its destination, and has fewer than 2 moves or no shots, and is not archers or has no shots, it takes that enemy as its target and stops. If the enemy is in range and the unit has moves and shots and no target, it shoots once and checks again.

**Shooting** (`FUN_0043910C`; report §4). Light infantry (range 1), archers (range 2) and light cavalry (range 1) shoot; heavy infantry and heavy cavalry have no shots. The range test is `distance ≤ range`, with no line of sight. With `s` the shooter and `t` the target, and `vuln` the target type's shooting vulnerability (light infantry 18, heavy infantry 2, archers 18, light cavalry 15, heavy cavalry 4):

```text
shots_s -= 1; moves_s -= 1; target_s = none
base = (troops_s × quality_s × morale_s × vuln[type_t]) div (troops_s × 5 + 150000)     (32-bit)
if distance(s, t) < range[type_s]: base × 2                       (only archers at distance 1)
n    = min(base, min(troops_s div 3, troops_t div 2)) + 1          (the min taken in 16 bits)
loss = Random(n) + Random(n)
morale_t -= min(3, (loss × 35) div (troops_t + 1))                 (troops before the loss)
troops_t -= loss
Rout(t)
```

**Melee** (`FUN_004393EC`; report §5). At the end of the moving side's half-round, each of its slots in order that has troops, a target, and a target with troops fights it. With `a` the slot, `d` its target and `M` the rulesets' matrix, `M[attackerType][defenderType]`:

```text
f  = min(4, number of the side's slots, alive or not, whose target is d)       (at least 1)
A  = (M[type_a][type_d] × troops_a × (quality_a × 10 + morale_a)) div 2000 + 12
D  = (M[type_d][type_a] × troops_d × (quality_d × 10 + morale_d)) div 2000 + 12
nA = ((troops_a × D) div A) div 12 + 1
la = min(30000, ((Random(nA) + Random(nA)) × (5 − f)) div 5);  la = min(la, (troops_a × 4) div 10) + 1
nD = ((troops_d × A) div D) div 10 + 1
ld = min(30000, ((Random(nD) + Random(nD)) × (2f + 5)) div 5); ld = min(ld, (troops_d × 4) div 10) + 1
if troops_d div ld < troops_a div la: morale_a = min(99, morale_a + 2); morale_d = min(99, morale_d − 3)
else:                                 morale_a = min(99, morale_a − 3); morale_d = min(99, morale_d + 2)
troops_a -= la; troops_d -= ld
Rout(a); Rout(d)
```

A target persists until its side's next half-round setup. The side that lost the larger fraction of its troops takes −3 and the other +2, ties going against the attacker. Each side's loss is capped at 40 % of its own troops, plus 1.

The hook replayed these two formulas on every exchange of 318 battles, the 315 sweep battles and one natural Rome–Gaul pair over three seeds: 5,829 shots and 3,510 melees, each with the predicted range `n` for its draws (the archers' doubling at distance 1 and the 16-bit `min` included) and the replayed troops and morale equal to the next snapshot in every slot, 0 differences. Changing one constant on real battles makes it miss: the matrix entry heavy infantry against heavy infantry 5 → 6, or light infantry's vulnerability 18 → 17. The 32-bit wrap was not needed to explain any melee **[Wine candidate: hook]**.

**Morale and rout** (`FUN_00438FB0`; report §6). Morale starts as in copy-in and changes only by these: a shot hit, `−min(3, (35 × loss) div (troops + 1))` to the target; a melee, +2 or −3 as above; a friendly unit routing, −6 to every live friend; an enemy unit routing, +5 to every live enemy, capped at 99. There is no floor and no recovery between half-rounds.

```text
Rout(u):
  if troops_u ≥ standardBattalionSize(type_u) div 25 and morale_u > 19:
      if morale_u > 39: return
      if Random(morale_u) + Random(morale_u) > 29: return
  remove u (troops 0, its cell empty)
  every live friend: morale −= 6; if morale < 30: remove it (no further cascade)
  every live enemy: morale = min(99, morale + 5); if its target is u: target = none
  if either side has no live unit: the battle is over
```

The hook found the predicted number of draws in all 12,849 rout tests of its 318 battles (188 drew, 547 units removed, cascades included), the replay matching the snapshots **[Wine candidate: hook]**. Its report words the drawing band as `20 < morale ≤ 39`, where the code read gives `morale > 19`; the two differ only at morale 20, and the report does not say whether a test at 20 occurred, so which the original applies there is still open on the research side.

**Surrender and the end** (report §6, §8). *Surrender* (after "Are you sure you want to surrender ?", a box with **Yes**, **No** and **Cancel**, where No leaves the battle and its block unchanged **[Wine candidate: sweep, B8]**) removes every unit of the side, with no cascade, ends the battle and ends the half-round. The battle is over when, after any rout or a surrender, one side has no live unit, and **nothing else ends it**: no half-round limit, no retreat. The battle window cannot be closed while the battle lasts, except by quitting the application. The winner is the attacker if any attacker slot has troops, else the defender; if both sides are emptied, the defender "wins" with no units **[derived: an unexercised edge of the same code]**. In the sweep's 315 battles, every side played by the general, no side surrendered, no battle ended with both sides emptied, and none ran longer than 35 half-rounds (8 to 35, mean 15.2, the longest the three-against-three mirror cells) **[Wine candidate: sweep, B5]**.

**Write-back** (`TBattleOver_InitializeForm` and `TBattleOver_OK`; report §9). The result window, **Battle ended**, shows `"W's  army  defeats  L's  army."`; per type and in total, the winner's troops at the start (its army before the write-back), the winner's survivors, and the loser's troops at the start; `"The army of W captured N talents."` (or `"no money."`); and `"… N tons of supplies."` (or the original's `"no suuplies."`). Its **OK** does, in order:

1. The winner army's 20 units are zeroed, and each surviving battle slot, in slot order, is copied into units 0, 1, … (origin, type, troops, name), each with `quality = max(6, quality)` and then, on `Random(4) = 0`, `quality = min(9, quality + 1)`. The hook counted one `Random(4)` per surviving winner unit in all 315 sweep battles, and the sweep saw 146 promotions, each a surviving winner unit's quality 6 → 7 **[Wine candidate: hook; sweep, B5]**.
2. The winner's money gains the loser's money; its supplies gain the loser's and are then capped at `totalTroops div 100`. In the sweep each of Gaul's 182 wins captured the 156 talents Rome's army carried, and Rome's 133 wins captured nothing from Gaul's empty purse **[Wine candidate: sweep, B5]**.
3. The winner's marker is redrawn and the loser army is deleted.
4. Unity: the winner `min(990, unity + 25)`, the loser `−25`.
5. News: `"W destroys army of L."`.
6. The peace dialog: in a human–computer battle with `strength(W) < strength(L)`, `unity(L) > 500` and `cities(L) > 7`, a `Random(5) < 2` drawn after those tests offers the treaty. The probe saw this **Offer of peace** box ("An honourable peace with no reparations …", Yes and No) after 3 of 16 human defeats from one start save, and the sweep after 2 of 3 seeds, the same in every run of a seed, which fits one seeded draw; in the sweep's 315 battles it appeared in 76, every one a win for Gaul, the computer nation, over Rome, the human nation under *Computer general*. The hook saw the `Random(5)` drawn in 185 of its 318 battles and the box open exactly when the draw was below 2, 77 of 77. A seeded experiment then measured the three tests as strict thresholds, read after the battle's write-back: the loser's unity 501 opens and 500 does not, its city count 8 opens and 7 does not, and a winner with the larger army sum gets no box; when a test fails, no draw is made. It answered the box both ways on 12 pairs of runs. **Yes** sets the relation between the two nations to −18 in both directions and appends `"W and L have agreed to end their war."` to the news, and no other decoded field of the save changes; at the next End turn the −18 had thawed to −14. **No** changes no decoded field of the save. When the box opens, the game reseeds `RandSeed := winner + loser`. Not measured: equal army sums, two humans, and the treaty's ally loop **[Wine candidate: probe; sweep, B4, B5; hook; the experiment, [`2026-10-05-battle-peace-offer.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-05-battle-peace-offer.md)]** ([`decompiled-war-cascade-and-peace-paths.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-war-cascade-and-peace-paths.md); Diplomacy); between two humans, `THVHBatPols` always.

The probe read the window and its effects from one battle exactly as above, the original's `"no suuplies."` included: Gaul's 46,700 against Rome's 37,081, Gaul finishing with 17,239, "The army of Gaul captured 156 talents.", Rome's unity 881 → 856 and Gaul's 402 → 427, and the news line in the next save **[Wine candidate: probe, item 1]**. There is no other strategic morale change: a computer side keeps its copy-in `+3`. The loser's units that routed or surrendered are gone with its army, as the instant path's loser is.

**The computer general** (report §2, §7).

- **Placement** (`FUN_004381A4`). It clears the side's cells and draws `r = Random(5)`. The base row is 2 stepping −1 for the attacker, 9 stepping +1 for the defender. For each block `g = 0 … 3`, it takes type `t = Form[r][g]` and columns `3g + 1 … 3g + 3`, and places every live own unit of type `t`, in slot order, filling the columns and then the next row; after the third row it stays on the third row, so a block of more than 9 units **stacks units on occupied cells**. When `t` is heavy infantry, archers follow in the same block, continuing the same counters. `Form` is the DAT's table at `0x479078` (DAT `0x1F3B8`):

  | r | Columns 1–3 | Columns 4–6 | Columns 7–9 | Columns 10–12 |
  | --- | --- | --- | --- | --- |
  | 0 | HC | HI + Ar | LI | LC |
  | 1 | LI | HI + Ar | HC | LC |
  | 2 | LC | HC | LI | HI + Ar |
  | 3 | LC | LI | HI + Ar | HC |
  | 4 | HC | LC | HI + Ar | LI |

  The hook counted exactly two placement `Random(5)` draws per battle, one per side, with Rome a human nation under *Computer general*: the draw belongs to whichever side the general places, not only to a computer nation **[Wine candidate: hook]**. In the sweep's 315 battles the defender stood on row 9 and the attacker on row 2, a block three cells wide wrapping to the next row, and the defender's columns changed with the seed, its army and the number of attacker units (the attacker's copy-in draws come first), never with the attacker's type **[Wine candidate: sweep, B5: consistent with the table, not derived from it]**.

- **Movement**: Pass 1 (`FUN_0043A31C`) uses types `[1, 4, 3, 0, 2]` (`0x4790A0`: heavy infantry, heavy cavalry, light cavalry, light infantry, archers), then ascending live slot within each type. Pass 2 (`FUN_0043A544`) and the threat/flank loops (`FUN_0043ABB4`) use ascending own slot directly **[confirmed: code, [target-rule clarification](https://github.com/diegoami/imperial-conquest-2-research/blob/93bee8965e5d0d05017deb3b31d5289f7af263c0/docs/reports/2026-10-16-tactical-target-and-draw-attribution.md#e-iteration-claims-and-remaining-flank-details-code-attribution-open)]**.
  - **Pass 1, choose and engage.** Target choice (`FUN_00439E08`): light infantry prefers archers, then light infantry, then any; heavy infantry prefers heavy infantry, then any; heavy cavalry prefers heavy infantry, then any; archers and light cavalry take any. Among the live enemies of the wanted type it takes the smallest `v = troops × quality × morale × M[theirs][mine] div 10000`, with `v div (c + 1)` when `c` (the focus count plus the claims) is below 4, and `v × 2` otherwise; ties go to the first, and the claim is recorded. The original records actor→target words and counts matching words; the port stores counts by target. Those representations agree for an uninterrupted once-per-actor Pass 1; representation alone establishes no defect. Original runtime claims are absent from hook logs and saves **[confirmed: code; observation limit, [clarification](https://github.com/diegoami/imperial-conquest-2-research/blob/93bee8965e5d0d05017deb3b31d5289f7af263c0/docs/reports/2026-10-16-tactical-target-and-draw-attribution.md#e-iteration-claims-and-remaining-flank-details-code-attribution-open)]**. Engage (`FUN_0043A160`): archers with shots at distance below 3 fire until moves or shots run out or the target is removed; otherwise, if adjacent, the unit shoots while it has shots until it has 1 move or no shots, then takes the enemy as its melee target if it lives; otherwise, if the line is clear, it moves toward the target; otherwise it moves toward the nearest empty cell with a clear line in the `(2r + 1)²` box around the target (`r` 2 for archers, 1 otherwise; `dx` outer, `dy` inner, strict `<`).
  - **Pass 2** (`FUN_0043A544`), for each unit with moves and no target: a unit with shots scans live in-range enemies in slot order, minimizing `trunc(enemyTroops / s)`, with best ratio initially 20000 and strict `<`. Here `s = ShotBound(actor,enemy)`; if the enemy has shots, replace the divisor by the signed-word `s + trunc(s/4)` **before division**. It fires until its moves run out or the target is removed. **The loop does not check shots, so shots can go negative.** Without rechecking moves, it scans adjacent candidates using `S(u,v) = trunc(troops[u] × quality[u] / 100) × morale[u] × M[type[u]][type[v]]`, preserving 32-bit wrapping and signed division. For each candidate, `adjusted = S(enemy,actor) − focus × S(enemy,actor)`; filter by `trunc(2 × adjusted / 3) < S(actor,enemy)`, then keep the strict minimum adjusted value below initial 100000000. Focus counts all 20 own target words, including dead slots **[confirmed: code; weighted melee also x86, [Pass 2](https://github.com/diegoami/imperial-conquest-2-research/blob/93bee8965e5d0d05017deb3b31d5289f7af263c0/docs/reports/2026-10-16-tactical-target-and-draw-attribution.md#a-pass2-weighted-strength-and-eligibility-codex86) and [shooting clarification](https://github.com/diegoami/imperial-conquest-2-research/blob/93bee8965e5d0d05017deb3b31d5289f7af263c0/docs/reports/2026-10-16-tactical-target-and-draw-attribution.md#additional-source-clarification-from-intake-shooting-target-divisor-code)]**.
  - **Pass 3** (`FUN_0043ABB4`). For each unit with moves and no target, threat mode is selected by the **actor**: an archer with shots > 0 uses `−ShotBound(actor,enemy)` for every enemy and box radius 2; all other actors, including exhausted archers, use enemy weighted strength `troops × quality × morale × M[enemy][actor] div 10000` and radius 1. Fill all 20 enemy entries, dead key 1000000; find the first strict minimum of each remaining suffix, then make **one swap** after that suffix scan. Stop considering keys above 999999. Move toward the first enemy with a clear line, or an empty cell with a clear line in its box. Then pass 2. Then the **flank**: each unit with no target whose moves are untouched (or are 1, with the counter below 10 and a type other than heavy infantry) takes `h = −1` if the enemy's captured `minX ≤ 13 − maxX`, else `+1`; the bounds/flag are captured before threat movement and nested pass 2. `Random(3) = 0` flips `h`. Count each live enemy strictly below as +1 and every other live enemy, **including equal Y**, as −1; `v` is +1 only for a positive balance, otherwise −1. **Every random draw, in order** (report, "Every `Random` call, in draw order"). The draws are, in this order: copy-in's `Random(quality × 4)` for each live attacker slot and then each live defender slot (`Random(0)` still consumes a draw); `Random(5)` for each computer side's placement, defender first; in each movement half-round, in the order the computer general's passes or the human's orders make them, two draws per shot and then `Rout(target)`, two draws per `Rout` only when its unit has at least the floor and morale 20–39, and one `Random(3)` per flank; at the end of each half-round, per own slot in order, four draws per melee (attacker, attacker, defender, defender), then `Rout(attacker)`, then `Rout(defender)`; after the battle, `Random(4)` per surviving winner unit in slot order, then the possible `Random(5)` of the peace dialog. The hook logged every draw of 318 battles on the lab build and found this order with no mismatch: each draw's range equal to the one the state predicts, the seed chain unbroken from the battle's start to the last post-battle draw, and no draw unexplained or missing; only the number of flank draws cannot be predicted from the snapshots, since it depends on the general's moves inside the half-round **[Wine candidate: hook]**. The port draws through one seam with the original's `Random(n)` semantics: a value in `[0, n)`, and `Random(0)` returning 0 and still consuming a draw. In play the seam reads the game's seeded `IRng` (principle 4), on a stream of its own per battle **[designed: the stream; confirmed: the order and the semantics]**. **What `improved` changes** (the user's decisions of 2026-10-04 on [#496](https://github.com/diegoami/imperial_conquest_2/issues/496)). These rules are **[designed]**: none comes from the original. Each is one ruleset switch or value in `improved`'s `combat.tactical`, and `classical-faithful` keeps the original's behaviour in every one. The user confirmed T130's complete cap/remnant/pursuit design on [PR 1142](https://github.com/diegoami/imperial_conquest_2/pull/1142#issuecomment-6215718392), for `improved` only; the original behavior remains the classical default.

- **Mid-battle save** at the start of a half-round only (Saves, above).
- **The code quirks are fixed.** Pass 2's shooting loop stops when the unit has no shots, so shots never go below 0; the products are computed in 64 bits, so nothing wraps; and placement never stacks: a block with more than nine units continues into the next empty cell of the side's home rows, in row order, and a unit that finds no empty home cell keeps its copy-in position.
- **No slow advance**: a computer side's units get their full moves from the first half-round.
- **A half-round cap of 100** **[designed, user-confirmed on [PR 1142](https://github.com/diegoami/imperial_conquest_2/pull/1142#issuecomment-6215718392)]**. Count completed half-rounds including placement. Finish that half-round's exchanges first; a natural victory takes priority, otherwise end before setup 101. The defender holds, attacker withdraws, and both keep their on-board survivors; routed units follow the survival rules below. The attacker pays retreat losses and scatters through the existing placement rule (or is destroyed if empty/boxed in), with campaign moves spent; the defender stays put with unchanged campaign moves. No cap promotion, money/supply transfer, unity change, peace offer/draw or new withdrawal news line; each keeps its money and own supplies capped to remaining troop capacity. The result identifies the cap/withdrawal. Searched the original tactical decompile §§4–9 and sweep B5 (research `87d1571`): the original has no cap; the 315 small, single-type, quality-6 computer battles lasted 8–35 half-rounds (mean 15.2; longest HI mirrors 28–34 and HC mirrors 21–35), one geometry and no human side. This supports headroom from below, not an upper bound for full/mixed armies; 100 is a designed guard.
- **Scatter after a loss** **[designed, same confirmation]**. The remnant keeps every positive troop remaining immediately before direct rout or the one-level cascade removes a unit. Actual casualties stay lost. Live troops surrendered on the board are captured; earlier routed troops can escape. At the cap, live withdrawing attackers join their prior routes. Preserve type, origin, name and quality in original slot order. The winner's routed troops rejoin at exit strength without promotion; only on-board winners draw promotions. Ordinary victories retain captured money/supplies and unity effects; a losing remnant carries zero money/supplies, zero moves and unchanged strategic morale. Empty or boxed-in remnants are destroyed with references cleared; publish scatter only on escape and destruction only on actual destruction. Optional saved routed counts are absent under classical and default to zero in legacy saves. The searched decompile instead zeroes removed units and deletes the loser; it establishes no escape/rejoin fraction.
- **Retreat losses** **[designed, same confirmation]**. Pursuit weights per troop are LI 1, HI 1, archers 2, LC 4, HC 3; only live on-board winners pursue. With weighted pursuit `P` and pre-loss remnant size `R > 0`, `fraction = min(500, 50 + floor(100 × P / R))` over denominator 1000; each unit independently loses `floor(troops × fraction / 1000)` in wide arithmetic. Base 5%, scaling 10%, cap 50%; no variance draw, minimum-one loss or redistribution. The same losses apply to capped attackers. Ordinary promotion draws and the possible peace draw precede restoring routed units, calculating retreat losses and drawing the unchanged scatter distance last. Peace gates see the loser removed before escape, as original tactical write-back does; cap has no promotion/peace draws. `retreatLosses` and `winnerRoutedUnitsRejoin` are false under classical; disabled/dormant parameters add no behavior or draw. The original decompile's exchange caps and the sweep establish no pursuit formula or weights: these choices implement the user's direction and require play balance, not a claim of original evidence. The instant path and its defeat selector remain unchanged.

### Diplomacy — **[mostly confirmed; only the AI's decision-making is designed]**

**This section's original premise was wrong.** It said diplomacy "lives in unnamed AI-only code, never reached by name — genuinely not recoverable". That conclusion came from decompiling `TPolitics_MakePeace` alone; the rest of the system is in `TPolitics`, `TBattlePols` and `FUN_00450C68`, all reachable by name. See [decompiled-diplomacy-peace-terms-and-instant-battles.md](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-diplomacy-peace-terms-and-instant-battles.md). What is actually confirmed:

- A 16×16 relation matrix (nation record `+0x26`), kept symmetric by the setters except that a rebirth leaves it one-sided (`2026-10-12-g4-followups.md` case J, a Wine candidate), with states `0` peace, `1` trade, `2` alliance, `3` war, and **negative values as cooldown counters** — `−8` after breaking trade, `−24` after breaking an alliance, `−18` after ending a war — that thaw quarterly **[confirmed]**. Each visit of a negative cell sets it to `v + 1`, or, when `Random(3) = 0`, to `min(0, v + 3)` instead. The loop visits rows 0–15 and columns 0–7 only, and the setter writes both sides. So a pair with one index below 8 thaws once a quarter, a pair with both below 8 is visited twice and can thaw twice (the peace offer's −18 → −14 is one `+1` and one `+3`), and a pair with both at 8 or above never thaws **[confirmed: code re-read at `FUN_00451B40` :54908–54931; seen under Wine as Seleucid (2) ↔ Galatia (12) −8 → −7 on both sides, and Media (14) → Galatia (12) staying −8: [war cascade row 8](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-war-cascade-and-peace-paths.md), [atlas increment 11](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-21-original-sav-semantic-atlas.md)]**.
- **Making peace from the International relations screen** is not limited to war: the Peace radio on a trade partner, then OK, sets the relation to −8 on both sides, and on an ally to −24 on both sides, with no box and no news line; the cooldown survives End turn, and Cancel discards the click **[confirmed: Wine for the trade case and Cancel; the alliance case was staged; [`2026-10-09-peace-radio-ends-trade-and-alliance.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/75a30cd/docs/reports/2026-10-09-peace-radio-ends-trade-and-alliance.md), research `75a30cd`]**.
- **Maximum 3 trade partners** per nation; trade is refused while a cooldown is active or while allied/at war **[confirmed]**. The original's lines, in the order it tests them: the proposer's own 3 partners, *"You can only trade with 3 nations."*; a cooldown, *"X does not want to trade with you."*; an ally, a nation at war, or a target with 3 partners and no pending trade offer from that same target, *"You cannot trade with X."* (there is no "already trades with" line) **[derived: code, `TPolitics_MakeTrade` :55190–55268; Wine candidate: [`2026-10-12-g4-followups.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/0b0b55e/docs/reports/2026-10-12-g4-followups.md), research `0b0b55e`, B, each case with a target at peace as the control]**. The clone's wording and order differ (#801).

Run live, a war declared by attacking Carthage's fleet from trade terms reached Carthage's ally Numidia (peace → war) and left Greece, on trade terms with both, unchanged; the news gave the declaration on the target first, then the one on its ally **[Wine candidate: [`2026-10-03-fleet-peace-prompt.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-03-fleet-peace-prompt.md)]**. 1. **Economy phase**: recruit/build up to an affordability threshold scaled by `expansionDrive`, prioritizing whichever unit types the effectiveness matrix suggests counter a currently-visible threat. **Since T157, under `classical-faithful` the economy phase is the original's** (`flags.aiEconomy = original`; [`2026-10-07-strategic-ai-turn.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-07-strategic-ai-turn.md) §2.1–2.3): recruitment follows the threat budget, with the original's city choice, the 8-a-turn and 3-below-the-floor gates, and its types and amounts; the tax rate changes only in week 11, by the original's three rules; and the AI never orders a fortification. 2. **Military phase**: evaluate each border city's threat level (visible enemy strength within N tiles) against its own garrison; reinforce, hold, or — if `aggression` and a favorable strength ratio both clear a threshold — attack. **Since T82, the AI attacks and besieges only nations it is already at war with**: an attack is never an implicit declaration. The AI never declares war on an ally that holds a city. The pick includes human seats: Carthage declared on human Rome on the 14th turn with every gate met, and the human got only the upper-cased news line, no box. An AI alliance also puts a human at war through the setter's cascade: Illyria allied with Gaul, which was at war with Rome, and declared war on Rome, ending their trade, with no prompt **[confirmed: one staged Wine run, each path once; [`2026-10-22-manual-gaps-disband-purchase-storm-ai-war.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-22-manual-gaps-disband-purchase-storm-ai-war.md) §4, research `0658ff3`]**.
3. **Diplomacy phase** (since T82, the original's rule): an alliance only against a common enemy, on `Random(20) == 0` when not busy; trade with up to 3 partners, swapping a poorer partner for a richer one, which leaves the dropped partner at the −8 trade cooldown and is the usual source of a −8 in play (the swap does not test that the dropped partner is alive) **[derived: code, `FUN_0044FB7C` :53436–53449; Wine candidate: [`2026-10-12-g4-followups.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/0b0b55e/docs/reports/2026-10-12-g4-followups.md), research `0b0b55e`, J]**; and every trade and alliance written only with a computer partner. An AI's offer to a human is a notice the human may accept through the ordinary proposal rules. At each human turn start one nation is drawn (`Random(16)`), and it offers only if it is at peace with the human, alive, a computer seat and wins `Random(3) == 0`: trade when its tax base is above the human's poorest partner's (0 with fewer than 3) and one of its partners is poorer than the human, alliance instead when it is a neighbour and the human is at war with no one **[derived: code, `FUN_00452034` :54979–55026]**; over three 60-round variants every offer came from an eligible proposer, at the predicted rate, and alliances only with the human at war with no one **[Wine candidate: [`2026-10-12-g4-followups.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/0b0b55e/docs/reports/2026-10-12-g4-followups.md), research `0b0b55e`, K]**. The AI never seeks peace on its own (since T88, the original's rule). Towards a human, peace comes only through the post-battle treaty, which the human accepts or refuses (`peace-yes` / `peace-no`).
4. **Victory-awareness**: nations close to the scenario's victory condition weight their decisions toward securing it (e.g., a domination-victory AI prioritizes attacking weak neighbors over turtling).

**Faithful recruitment accounting.** [T192](tasks/T192.md) uses the shared army helper for own/allied/enemy/proximity army contributions: per slot, truncate `weight × troops / 100`, sum, truncate `/ 80`, then multiply by army morale. Recruitment queues use raw training power instead: `Q = trunc(troops / 100) × weight`, stored as a signed 16-bit value for each visited existing queue but accumulated as an integer for a successful new queue. One accumulator counts every actually visited occupied queue before eligibility plus successful new orders; a separate accumulator counts only successful mobilizations. Preserve the original indexed compaction skip, initial deficit/readiness snapshots and existing resource/order gates. New orders stop after the first success that reaches or crosses the initial deficit minus visited existing power, before another order draw. The bounded correction retains aggregate allied/proximity division and inclusive capital-distance bounds pending [issue 1245](https://github.com/diegoami/imperial_conquest_2/issues/1245); it does not establish complete original-budget equivalence. The approved historical treaty continuation is an unedited native port-JSON test save, not original-game SAV export evidence ([source disposition and limits](tasks/T192.md), [production accounting](../src/IC2.Engine/Ai/AiFaithfulEconomy.cs)).

This is intentionally simple to start — a heuristic scoring function per candidate action, pick the highest score, no search/lookahead — because it's easy to reason about, easy to tune via data, and easy to unit-test (given a world state, assert the AI picks the expected action class). More sophistication (lookahead, learning) is explicitly future work, not needed for a first playable version. The all-AI soak tests fail on a **full-round stall** (every live seat idle, with no command and no substantive state change, for a whole round), not on idle neighbours in turn order: a nation with no army that spent its seasonal payout has no affordable action until the next one, which is legal play ([#1290](https://github.com/diegoami/imperial_conquest_2/issues/1290), closing #268).

### Victory conditions — **[the original's is confirmed; the alternatives are designed]**

The original's own condition *was* recoverable, contrary to this section's earlier claim: `THumanFalls_InitializeForm` (`0x00455E38`) tests the nation's city count against **334, the total number of cities on the map**, and awards *"You have conquerred the Mediterranean, a unique achievement."* — total conquest is the only win. The same screen compares the year against **250 BC** (start is 270 BC) and reports the reign's length **[confirmed: decompiled-diplomacy-peace-terms-and-instant-battles.md]**. The turn-start check `FUN_00452034` tests the year against 250 BC **[derived: decompile, :55032–55036]**. 250 BC is a real end, not only the screen's wording: a staged play reaching 250 BC opens the window *"You have reached the end of your allotted 20 years."* for each human seat in turn, and victory too ends the human's game through the same window, which then hands the seat to the computer **[Wine candidate: [`2026-10-05-end-of-game-screens.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-05-end-of-game-screens.md), research `d1b5983`, W4, W5, W6, W11, W12; staged states]**. Whether a computer nation that takes every city ends the game too (the conquest path tests the conqueror's count without testing that it is human, **[derived]** only) stays unread and outside `v0.5.0`: a research request after the release (the user's decision of 2026-10-05). Whether total conquest should be the shipped default was **open question Q5** in [design-audit.md](design-audit.md) — now answered: yes, as the `classical-faithful` default; `improved` defaults to a friendlier condition (see "Two shipped presets" above).

Scenario-configurable, default set to ship **[designed]**:

- **Domination**: control every city, or every city belonging to nations still at war with you.
- **Score at turn limit**: a weighted sum of cities held, treasury, and unity, highest wins.
- **Scenario-custom**: an explicit goal defined in the scenario file (e.g., "hold these 3 named cities on turn 50") — this is what makes custom scenarios interesting beyond "same rules, different map."

## The scenario system

A `Scenario` file is the actual moddable/shareable unit:

```json
{
  "id": "fall-of-galatia",
  "world": "classical-mediterranean",
  "ruleset": "classical-faithful",
  "seats": [ { "nation": "rome", "control": "human" }, { "nation": "seleucid", "control": "ai", "personality": { "aggression": 0.8 } } ],
  "victory": { "type": "custom", "goal": "..." },
  "turnLimit": null
}
```

Authoring is by hand-written JSON for the initial version ([scenario-authoring.md](scenario-authoring.md) is the field reference, with the `example-*` scenarios in `data/`) — no in-game editor yet (explicitly future work; not needed to have a playable, moddable game). A `World` can be reused across many `Scenario`s (same map, different starting setups/rules), and a `Ruleset` can be reused across many `Scenario`s and `World`s alike (a "hard economy" ruleset variant could apply to any map).

## Asset packs — **[designed]**

An `AssetPack` is a manifest mapping stable string keys to files:

```json
{
  "unit.light_infantry.icon": "units/light_infantry.png",
  "terrain.plain.tile": "terrain/plain.png",
  "sfx.city_captured": "sfx/capture.ogg"
}
```

The repo ships a default pack built from freely-licensed/generated placeholder art and audio — good enough to play and test with, never blocking development on asset availability. A different pack (a fan-recreated "authentic style" set, or the user's own commissioned art) is a drop-in manifest + files; original copyrighted assets never enter the repo, consistent with the existing DAT/EXE/WAV policy already in place for the RE work.

### Army and fleet markers scale with size — **[confirmed]**

Decompiled after this requirement was first raised from a confirmed-in-play recollection: `TUnitMap_SelectUnit`'s marker arithmetic proves the original map cell code itself encodes a **three-tier size band**, not just owner — see [`decompiled-unit-map-orders-and-record-fields.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-unit-map-orders-and-record-fields.md):

```
armyMarker  = owner + (troopsThousands < 25 ? 200 : troopsThousands < 50 ? 216 : 232)
fleetMarker = owner + (shipCount       < 25 ? 300 : shipCount       < 50 ? 316 : 332)
```

Three army tiers (< 25,000 / 25,000–49,999 / ≥ 50,000 troops) and three fleet tiers (< 25 / 25–49 / ≥ 50 ships; the help file's "10..25 / 26..50 / 51..100" is off at both boundaries, [H05](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-08-help-reference-tables-h05.md)), each 16-wide (one slot per nation), which is also why `(code − 200) % 16` / `(code − 300) % 16` recovers the owner regardless of tier — the band was hiding in plain sight in the same arithmetic that gave the owner. `TUnitMap_SelectUnit` accepts exactly `200..247` for armies and `300..347` for fleets, matching. The army boundaries are seen in play too: 24,999 / 25,000 / 49,999 / 50,000 troops give map words owner + 200 / 216 / 216 / 232, and the word is stored, not recomputed on a load: `FUN_0044a80c` rewrites it only when the army changes (a mercenary hire, a Join, a transfer), so an edited save keeps a stale band until then **[Wine candidate, [`2026-10-08-army-marker-size-band-on-the-map.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-08-army-marker-size-band-on-the-map.md), research `be0691a`; the callers derived]**. The band also picks the icon on the unit map: three army icon sizes (a small soldier with a spear, a medium one, and a large one with a bigger shield and a mace) and three fleet icons (a small sailboat, a galley with three shields along the hull, and a larger galley with a bigger sail and four shields). The original chooses the icon by the **stored** word, not by the troops or ships: a 24,999-troop army whose word was patched to 232 draws the large icon, and a 50-ship fleet patched to 300 draws the sailboat **[Wine candidate, [`2026-10-08-army-icon-follows-the-size-band.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-08-army-icon-follows-the-size-band.md), research `bff6bff`, and [`2026-10-08-fleet-marker-band-and-icon.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-08-fleet-marker-band-and-icon.md), research `f9d061a`]**. Every owner draws the same six shapes in its own three colours: the background of its city marker and two figure colours **[Wine candidate, [`2026-10-09-owner-colours-by-band.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-owner-colours-by-band.md), research `ba103a0`]**. They are six Rome-coloured templates recoloured at draw time from the nation record's `+0x424`/`+0x428`/`+0x42C`, which new-game setup writes as constants and the world exports as `battleColorsHex` **[confirmed: decompile + resources, [`2026-10-09-unit-icon-recolour-and-nation-glyphs.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-unit-icon-recolour-and-nation-glyphs.md), research `4ef90ec`]**. City markers carry the same three colours baked into their art, except Numidia's fill: teal on its cities, grey on its units (`asset-specification.md` §2). The fleet boundaries are seen in play as well (24 / 25 / 49 / 50 ships give owner + 300 / 316 / 316 / 332 after Join fleets), and Join fleets, Split fleet and Transfer ships each re-band every fleet they change, the split's new fleet included **[Wine candidate, the same fleet report and [`2026-10-08-split-and-transfer-reband-fleets.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-08-split-and-transfer-reband-fleets.md), research `0389684`]**. Storm losses and a naval battle's winner re-band through `FUN_0044b4f8` **[derived: a code reading, not run: the same report's review note]**, so in an unedited game a fleet's stored word matches its ships. An army's word is re-banded for a field battle's winner and for the surviving army of a mercenary desertion as well **[Wine candidate, [`2026-10-08-removed-army-restores-its-tile.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-08-removed-army-restores-its-tile.md) and [`2026-10-09-turn-end-and-ai-army-removals-restore-their-tile.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-turn-end-and-ai-army-removals-restore-their-tile.md), research `e6b4643`]**. Not every troop loss re-bands, though: an unedited save holds a Seleucid army of 37,821 troops under the ≥ 50,000 word, so a stale army word occurs in natural play **[Wine candidate, the turn-end report; which loss skipped the re-band is not known]**. **Every army removal run in play writes the army's covered cell back to the map** — disband, Join armies, a battle loss (tactical, and AI against AI), siege attrition, mercenary desertion and the conquest elimination, all through `FUN_0044AB90` — and record compaction keeps the moved record's marker and covered cell; only a removed fleet (`FUN_0044AD38`) writes 0 **[Wine candidate, [`2026-10-08-removed-army-restores-its-tile.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-08-removed-army-restores-its-tile.md), [`2026-10-09-siege-removed-army-restores-its-tile.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-siege-removed-army-restores-its-tile.md) and [`2026-10-09-turn-end-and-ai-army-removals-restore-their-tile.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-turn-end-and-ai-army-removals-restore-their-tile.md), research `e6b4643`; the defection elimination `FUN_0044BED8` runs the same army loop, derived: [`2026-10-09-defection-elimination-reachable-in-principle.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-defection-elimination-reachable-in-principle.md)]**. A fleet removed by a battle, a storm or its nation's conquest writes 0, and an army aboard a conquered nation's fleet is removed with no map write of its own: the army loop unlinks it from its carrier, then the fleet loop clears the fleet's tile **[confirmed: code; Wine candidate, [`2026-10-09-elimination-removes-fleet-and-army-aboard.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-elimination-removes-fleet-and-army-aboard.md) and [`2026-10-09-storm-sunk-fleet-clears-its-tile.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-storm-sunk-fleet-clears-its-tile.md), research `c288059`]**. The clone keeps no map grid, so a removed army leaves the terrain as it was, which matches; a removed fleet's calm cell is the deliberate difference [T81](https://github.com/diegoami/imperial_conquest_2/blob/archive/desktop-2026-10-20/docs/tasks/T81.md) records. **The clone keeps no stored word: it draws the tier of the current troop or ship count every time** (`godot/Assets/MapMarkerKeys.cs`, `ArmyIcon` and `FleetIcon`). ### City markers — **[confirmed]**: four population tiers plus the capital

Resolved 2026-10-07 (decompilation plan item 16) by [`2026-10-07-city-marker-variants.md`](https://github.com/diegoami/imperial_conquest_2-research/blob/main/docs/reports/2026-10-07-city-marker-variants.md): the map cell code size-bands cities the same way it does armies/fleets — `map code = 20 + owner + 16 × variant`, variants 0–4, occupied range 20–99 (20–199 was only the range searched). **Variants 0–3 are population tiers** on the city's current population in thousands — `< 25`, `25–49`, `50–99`, `≥ 100` — written by the original's marker writer `FUN_0044a794` **[confirmed: decompile]**. **Variant 4 is the national capital**: the writer refuses to touch a capital, and the variant-4 marker is written by the capital-relocation and rebirth paths; in eighteen saves every live nation's capital city and only those carry variant 4 **[confirmed: decompile + saves]**. Capital status does not layer onto a tier — it replaces it: a capital draws variant 4 regardless of population. This supersedes this section's earlier claim that a city's code was "purely its identity/index, with no population term in the arithmetic" — that reading was wrong, and the `[designed]` tier set it gated is now a confirmed four-tier split at the original's own boundaries. The five variants draw a small house, a house, a small castle, a large castle and a temple (the capital), each one fixed template in the owner's background, outline and fill colours **[derived: resources; drawn in Wine, a candidate until the desktop check, [`2026-10-09-city-marker-colours.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-city-marker-colours.md), research `cdffb27`]**.

One behavioural detail the reimplementation inherits knowingly: **the tier is refreshed only when a city changes owner, never by growth** — the writer's callers are the ownership-change paths (siege transfer, transfer/defection, elimination, conquest) and nothing in the weekly or quarterly tick calls it, so a city that grows past a threshold keeps its old, smaller icon until captured; the long-run saves hold variant-0 cities at population 26–28 **[confirmed: decompile + saves]**. The clone does not reproduce this staleness: it recomputes a town's tier from `PopulationThousands` on every draw, a recorded deliberate difference (`[designed]`, the user's decision of 2026-10-11 on bug [#818](https://github.com/diegoami/imperial_conquest_2/issues/818)). The original-compatible export writes the same current-population tier, so importing an original save and exporting it back refreshes every stale tier: three conquered cities of `fleet-port-antium-0734.SAV` (Bordeaux, Tarquinii, Tarrentum) come back one variant higher **[Wine candidate, one save: [`2026-10-29-export-city-marker-variant-and-empty-offer230.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/0b16319/docs/reports/2026-10-29-export-city-marker-variant-and-empty-offer230.md), research `0b16319`]**.

The reimplementation's keys: `city.tier1.icon` to `city.tier4.icon`, plus `city.capital.icon` for a live capital, with every ruleset shipping the thresholds `[25, 50, 100]` in `mapMarkers.cityPopulationTierThresholds`, since [T163](https://github.com/diegoami/imperial_conquest_2/blob/archive/desktop-2026-10-20/docs/tasks/T163.md): a non-capital town draws the tier of its current population and a nation's live capital the capital icon, in both packs.

## Original-save compatibility — **[confirmed format, designed policy]**

The SAV/DAT format's serialization shape is mapped ([`decompiled-sav-file-layout.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/decompiled-sav-file-layout.md) and its corrections); this does not establish a native-to-original mapping for every byte. Import policy: an imported original `.sav` always maps onto the shipped `classical-mediterranean` World and the `classical-faithful` Ruleset — those are the only numbers the imported state was ever balanced against. Attempting to load an original save into a game already using a different Ruleset or World is rejected with a clear message, not silently reinterpreted. This keeps `IC2.Data`'s hard-won parsers directly useful (the import path *is* `IC2.Data`, essentially unchanged) without requiring every custom ruleset to somehow stay compatible with 1996 byte layouts. The player opens one from Load game's Browse, which lists `.json` and `.sav` files in any folder and resumes an imported save as its own human nation(s); ordinary saving writes a remake `.json` (since [T165](https://github.com/diegoami/imperial_conquest_2/blob/archive/desktop-2026-10-20/docs/tasks/T165.md)).

**Original-compatible export [designed: user's planned 0.7.x requirement, #1191].** [T184](tasks/T184.md) provides the binary writer, [T185](tasks/T185.md) the native-state bridge/offline JSON converter, and [T186](tasks/T186.md) the existing File → Save As `.sav` option. Only validated shipped classical-mediterranean/classical-faithful strategic states are supported. Modified/custom worlds or presets, improved mechanics, active battles, unsupported controls and unrepresentable values are refused with reasons; exporting does not change state or advance play. Every live field is explicitly mapped and checked, every preserved private-template region justified, and encoding/width overflow fails without truncation. Unknown potentially-live bytes require evidence before export, not guessed defaults. The [evaluated safety finding](https://github.com/diegoami/imperial-conquest-2-research/blob/3bda5a0244b98e837e55269efe4eb552edfc4a65/docs/reports/2026-10-17-sav-export-live-regions-and-safe-rejection-policy.md) identifies the owned-city list as live and the 270-BC comparison baselines/conqueror as history; its 33-region nation accounting still leaves 31 UNKNOWN bytes (`+450..46A`, `+46D`, `+491..493`). Sampled zeros and same-template lineage do not justify preserving them after gameplay changes. Original constructors also leave army/fleet residue without a complete new-record policy. These source/public-save/bounded synthetic x86 findings are **[confirmed, partial]**; they do not establish changed-state export readiness or native Windows acceptance. Four bounded original-x86 helper paths neither read nor write the 31 UNKNOWN bytes, even when they hold nonzero patterned values; the three address-forming LEAs at `nation+450` feed the viewport fields `+486/+488`, not those bytes. With 812 indirect edges unresolved, this is bounded path conservation, not semantic closure (the whole-program search is research [#47](https://github.com/diegoami/imperial-conquest-2-research/issues/47)). Deleting a unit moves the last slot's full 32 bytes and clears only the vacated slot's troop count, and equal renames of equal visible names leave different string tails, so a normalized native unit list or name cannot rebuild original record lineage **[confirmed, partial: [bounded access and record lineage](https://github.com/diegoami/imperial-conquest-2-research/blob/51c98f1f8903822af1aca3bf2d876047bf1b7a8b/docs/reports/2026-10-18-sav-export-unknown-access-and-record-lineage-boundaries.md), research `51c98f1`]**. One changed-byte transformation is established: for an authentic envelope whose current nation is human (BYTE `+490` = 1), whose pending-offer source is −1 and whose viewport the refresh clamp leaves unchanged, the original Change Tax command (0..40) writes only that nation's tax WORD `+44A`. This comes from instruction slices; the GUI close/save composition and Windows acceptance are not established here **[confirmed, partial: [tax profile and binary aliases](https://github.com/diegoami/imperial-conquest-2-research/blob/51c98f1f8903822af1aca3bf2d876047bf1b7a8b/docs/reports/2026-10-18-sav-export-bound-tax-subset-and-binary-alias-evidence.md), research `51c98f1`]**. In the original Windows game, three tax-only outputs of that writer (Rome tax 0, Thracia tax 40, Rome tax 30 in winter) each opened, took an ordinary Recruit order and one End turn, saved, and reopened; each load save equals its candidate byte for byte and each reopen save equals its post-turn save **[confirmed: native Windows, bounded tax-only subset; partial: [`2026-10-18-sav-export-original-windows-tax-candidates.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/16f0193/docs/reports/2026-10-18-sav-export-original-windows-tax-candidates.md), research `16f0193`]**. ## Testing and determinism

- One seeded RNG service, injected everywhere randomness is used (combat rolls, weather events, AI tie-breaking) — never `System.Random` called directly in gameplay code.
- **Golden fixtures from real play**, not just hand-written unit tests: the project already has exact, documented before/after numbers for real game sessions —
  - the Rome/Gaul battle's exact per-type troop losses ([`full-battle-resolution-rome-vs-gaul.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/full-battle-resolution-rome-vs-gaul.md)),

  - the army-to-army transfer's exact reciprocal conservation ([`army-to-army-transfer-confirmed.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/army-to-army-transfer-confirmed.md)),

## Open questions genuinely left for later

A few things were deliberately deferred rather than decided here, because they don't block starting the build:

- Exact reparations/diplomacy formula tuning — ships as a placeholder, easy to retune once players notice it feels off.
- Whether hotseat's "blind handoff" screen should be on or off by default per scenario type — a UX call, not an engineering one.
- Whether a future in-game scenario/world editor is worth building, and when.
- Whether network multiplayer is ever pursued — the determinism-first design keeps the door open without committing effort now.
- Exact tuning of the `improved` ruleset's new `combat.onDefeat` scatter parameters (survivor fraction, scatter-tile range) — shipped with a documented placeholder default, meant to be retuned from actual play rather than derived from any original-game evidence, since the original has no partial-defeat outcome to measure against.
- **Remaining fidelity differences in the original's strategic turn**, now that it is decompiled ([`2026-10-07-strategic-ai-turn.md`](https://github.com/diegoami/imperial_conquest_2-research/blob/main/docs/reports/2026-10-07-strategic-ai-turn.md), all 4 in-play checks corroborated: the week-11 tax with a placement correction and the free mercenary hire by [`2026-10-07-ai-turn-corroboration.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-07-ai-turn-corroboration.md) §1–2, the intercept and the fleet hunt-or-port by [`2026-10-09-ai-intercept-and-fleet-hunt-in-play.md`](https://github.com/diegoami/imperial-conquest-2-research/blob/main/docs/reports/2026-10-09-ai-intercept-and-fleet-hunt-in-play.md)): the free mercenary hire already ships (T76) and the 2026-10-01 decision already points the faithful AI's recruitment at the original's rules ([#515](https://github.com/diegoami/imperial_conquest_2/issues/515)); the week-11 tax policy, recruiting into deficit down to `−wealth/500` and the threat budget are implemented by T157, with ready-unit mobilisation's original deficit and queue gates corrected by T171.
