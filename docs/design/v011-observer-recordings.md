## Capture and formats

Owner addition, 2026-11-08: verify actual resolution/frame rate for YouTube. Capture **native 1920×1080, square pixels, 16:9, constant 30 fps** using movie-only viewport overrides. Reject low-resolution native captures; do not upscale or inflate frame rate to claim HD. Verify source dimensions/rates and decode both MP4 outputs, requiring duration×30 frames and evenly spaced timestamps. Archive a separate H.264 High/CRF18 upload master with stereo 48 kHz AAC, alongside the web encoding. [YouTube encoding guidance](https://support.google.com/youtube/answer/1722171?hl=en) recommends matching recorded frame rate, progressive H.264/4:2:0 and fast-start MP4. [HD processing may finish after SD](https://support.google.com/youtube/answer/71674?hl=en); encoding cannot force every viewer's default quality. The subsequent owner instruction authorizes exactly one full-campaign pilot on the confirmed channel.

Deliver MP4/H.264, `yuv420p`, fast-start metadata, 30 fps and a native 1920×1080 viewport. Game audio, when enabled, becomes AAC. Autoplay starts muted. Optional WebM/VP9/Opus is a second encoding only if measurements justify its cost. AV1, GIF and HLS/DASH are not initial dependencies. [MDN's codec guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_codecs) describes browser/container tradeoffs; actual playback establishes acceptance.

Use Godot's [Movie Maker](https://docs.godotengine.org/en/stable/tutorials/animation/creating_movies.html), a real renderer, fixed FPS and a bounded frame budget. Capture OGV or short AVI, then encode with FFmpeg; AVI has a 4 GB limit. Linux automation uses Xvfb/software rendering, not the dummy headless renderer. Isolate user data and force authored media so local original-asset settings cannot enter footage. Do not record the desktop/private windows. Add observer scenario/seed arguments for reproducible jobs.
